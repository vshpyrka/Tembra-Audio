# Tasks: Metronome

**Input**: Design documents from `/specs/004-metronome/`

**Prerequisites**: plan.md, spec.md (clarified 2026-09-29, FR-001–FR-037), research.md (R1–R16), data-model.md (§1–§10), contracts/ (engine-c-abi-v3.md, metronome-audio-kotlin.md, metronome-domain.md, metronome-preferences.md, click-sounds.md, background-playback.md, metronome-screen.md, design-system-additions.md), quickstart.md.

**Tests**: Required. Constitution III (test-first, non-negotiable) and spec FR-033: every implementation task is preceded by the test that fails without it. Lanes, always with `--warning-mode all` from `app/` and always through the `gradle-run` skill wrapper (Constitution VIII): `./gradlew engineHostTest` (Catch2, host), `./gradlew checkAndroidHost` (JVM), `./gradlew checkIos` (simulator), `./gradlew checkAndroidDevice` (device), plus `./gradlew :androidApp:connectedDebugAndroidTest` for the app module's instrumented tests. Kotlin tests never link the engine; they use `FakeAudioEngine`, `FakeBackgroundPlaybackHost`, `FakeMetronomePreferences`, `FakeCustomClickSoundStore` and `FakeSoundFilePicker`. The real engine is exercised only by the `:shared:engine` device and simulator lanes.

**Skills** (Constitution VIII): before writing or reviewing any Kotlin or Compose task below, route through `using-chrisbanes-skills` and load the owner named in the task's contract: `compose-component-design` for every composable in contracts/design-system-additions.md, `compose-state-and-effects` and `kotlin-concurrency-and-flow` for the ViewModel, wiring and effects in contracts/metronome-screen.md, `compose-performance` for the draw-phase beat light, `kotlin-api-design` for the domain types and the platform seams, `compose-ui-testing-patterns` for every `uiTest` class, `gradle-run` for every Gradle command.

**Organization**: Setup adds the catalog entry, the glyphs, the platform declarations and the engine build inputs. Foundational builds what every story needs: the domain, the C ABI revision 3 with the engine core and the scheduler, the Kotlin `MetronomeAudio` seam, preferences and the sound store, tokens and generic components, the platform hosts and pickers, DI. Each user story is then an independently testable increment: US1 (tempo, play/pause, the beat light) is the MVP; US2 the bar shape and styles (with the debug Syncopated readings); US3 tap tempo; US4 the sound picker; US5 the custom WAV; US6 background playback and interruptions; US7 the wide and landscape layouts, input and screen-reader proof.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: no dependencies; T009 proves the catalog change before Phase 2 depends on Okio.
- **Foundational (Phase 2)**: depends on Setup; blocks every story. Inside it: domain tests (T010–T017) and implementations (T043–T049) first, because the engine facade (T063) and the ViewModel tests map `TickGrid` and `Tempo`; the C++ chain is T050 → T051 → T052/T053 → T054–T058 → T059 → T060 → T061 → T062; the Kotlin engine chain T063 → T064 → T065/T066; data T067 → T068; UI T069–T074 in parallel, then T075/T076 (platform), T077–T079, then the three checkpoints.
- **User Stories (Phase 3–9)**: all depend on Phase 2. US1 is the MVP and the base every later story extends (`MetronomeViewModel`, `MetronomeScreenContent`, `MetronomeSettingsPanel`); US2, US3, US4 extend it independently of each other; US5 depends on US4 (the picker's Custom entry); US6 extends US1's ViewModel; US7 depends on US2 and US4 (the panel and the tiles).
- **Polish (Phase 10)**: depends on every story.

### Within Each User Story

- Tests are written first and fail; models before the ViewModel; components before the screen composition; a review task against the named skills before the device check; screenshots and `NOTES.md` before the commit.

### Parallel Opportunities

- Setup: T003–T008 in parallel after T001–T002.
- Foundational tests T010–T042 all in parallel (different files); implementations marked [P] in parallel within their module; the C++ scheduler (T058) and the click synthesis (T054) in parallel once the headers (T053) exist.
- US1: T083–T088 in parallel; T089/T090, then T091–T094 in parallel, then T095.
- US2, US3 and US4 can be worked in parallel by different people after US1 (they touch different components; the ViewModel and the panel merges are small).
- US7's three test tasks in parallel.
