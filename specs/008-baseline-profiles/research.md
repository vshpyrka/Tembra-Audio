# Research: Baseline Profiles (feature 008)

**Date**: 2026-10-12 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Sources: the Baseline Profile Gradle plugin configuration page, the DEX layout (startup profile) page and the Macrobenchmark overview on developer.android.com (fetched 2026-10-12); Google's Maven index for current versions; Metro 1.0 docs; the Compose Multiplatform resources docs; the repository (`app/perf/tracepulse`, `app/perf-benchmarks`, `app/androidApp/build.gradle.kts`, `app/build-logic`). Facts the fetched pages did not state are marked *to verify in implementation* and are each covered by a quickstart step.

## D1. Baseline Profile Gradle plugin 1.5.0, consumer on `:androidApp`, producer in `:perf-benchmarks`

- **Decision**: `androidx.benchmark:benchmark-baseline-profile-gradle-plugin:1.5.0` (the same train as the Macrobenchmark 1.5.0 already in the catalogue; 1.6.0-alpha01 exists but is pre-release). The consumer plugin (`androidx.baselineprofile`) is applied to `:androidApp` unconditionally with `automaticGenerationDuringBuild = false` (default), `saveInSrc = true`, `mergeIntoMain = true` and no `filter` (the profile keeps the framework rules the journeys exercise, as the spec asks). The producer is the existing `com.android.test` module `:perf-benchmarks` (plugin applied there too, `useConnectedDevices = true`, no managed device). The app's `baselineProfile(project(":perf-benchmarks"))` dependency is declared only when `-Ptembra.perf` is present, because the module is only included in the build then (`settings.gradle.kts`).
- **Rationale**: the generated files land in `app/androidApp/src/main/generated/baselineProfiles/{baseline-prof.txt,startup-prof.txt}` (plugin default for `mergeIntoMain`), one location for every variant, consumed by every release-like build without further wiring. Keeping the producer in `:perf-benchmarks` reuses the journeys verbatim (FR-002) and adds no module. Applying the consumer unconditionally is the documented path and keeps the merge-into-APK step identical with or without `-Ptembra.perf`.
- **Cost to measure**: the plugin creates `nonMinified<Type>` and `benchmark<Type>` build types for every non-debuggable type, so `nonMinifiedRelease`, `benchmarkRelease`, `nonMinifiedPerf`, `benchmarkPerf` appear in `:androidApp`. Only `nonMinifiedRelease` is needed (the generation target); the other three are disabled in `androidComponents.beforeVariants` (the plugin's `warnings.disabledVariants` is turned off so it stays quiet). Host-lane and default-build durations are measured before and after (SC-007); **fallback** if the budget is exceeded: apply the consumer plugin only under `-Ptembra.perf` and register `src/main/generated/baselineProfiles` as a `baselineProfiles` source directory for ordinary builds.
- **Alternatives considered**: a separate `:baselineprofile` module (the AGP template) — duplicates the journeys or needs a third module to share them; `automaticGenerationDuringBuild = true` — runs devices during release assembly, the opposite of "regenerate on demand"; `mergeIntoMain = false` — per-variant files, and the `perf` type would need its own copy.

## D2. Generator and comparison classes live beside the benchmarks and are never run by a round

- **Decision**: `BaselineProfileGenerator` (`@get:Rule BaselineProfileRule`, one `@Test generate()`) and `ProfileComparisonBenchmark` (`MacrobenchmarkRule`, one test per journey) are added to `audio.tembra.perf` in `:perf-benchmarks`. The round command is unaffected because `tracepulse run` starts one `am instrument -e class <fqcn>` per journey class (`orchestrate_android.py`, `_JOURNEY_OF_CLASS`); it never runs the whole package. The plugin's own generation task passes `androidx.benchmark.enabledRules=BaselineProfile`, so when it runs the module it skips every `MacrobenchmarkRule` test.
- **Generator shape**: `rule.collect(packageName = PerfMetrics.PACKAGE, includeInStartupProfile = true) { pressHome(); startActivityAndWait() }` for the startup path, and a second `collect(..., includeInStartupProfile = false)` for the journeys: `TunerJourney().run(device)`, `MetronomeJourney().run(device)`, `StressJourney().run(device)` (each journey already takes a `UiDevice`; `MacrobenchmarkScope.device` provides it). `maxIterations` and `stableIterations` keep the plugin defaults (15 / 3): iterations repeat until three consecutive runs add no new rules, which is the "merged over repetitions" the spec requires and makes regeneration on an unchanged app differ only in ordering and timing-reached code. *Corrected in implementation (2026-10-12, baselines.md T019)*: the two collects live in **two `@Test` methods** (`startup()`, `journeys()`), because the plugin locates a test's profile files through the per-test output message file, which a second `collect` in the same test overwrites — the single-test shape lost the startup profile. The generator also grants `RECORD_AUDIO` in a `@Before`: the plugin's task installs the app itself (and uninstalls it afterwards), so the pipeline's install-time grant never applies and the tuner would open under the permission dialog.
- **Comparison shape**: the optimisation state comes from an instrumentation argument (`tembra.compare.state` = `none` | `profile` | `full`) read through `InstrumentationRegistry.getArguments()` and mapped to `CompilationMode.None()`, `CompilationMode.Partial(BaselineProfileMode.Require)` and `CompilationMode.Full()`; the journeys and metrics are the ones of the four existing benchmarks (`PerfMetrics.journey(name)`, `StartupTimingMetric`, cold start for startup, warm for the rest, 20 iterations). One `am instrument` per state keeps the benchmark JSON free of parameter suffixes, and the collector maps entries by **method** name (`startup`, `tuner`, `metronome`, `stress`) instead of class name. *Found in implementation*: Macrobenchmark 1.5 does not honour `androidx.benchmark.iterations` for `measureRepeated` (eleven-plus iterations with it set to 1 on the Pixel 6 Pro), so the comparison class reads `tembra.compare.iterations`; the round's classes are untouched (their `--iterations` default equals the code's 20, so the inert argument never showed there — a note for feature 007).
- **Alternatives considered**: `@Parameterized` over compilation modes in one run — the APK cannot then be reinstalled fresh between states (FR-008) and the JSON names carry `[mode=…]` suffixes the collector would have to parse; a second test module — duplicates journeys.

## D3. Shrinking with R8 on the release-like build types (owner's decision, planning input)

- **Decision**: in `:androidApp`, `release` gets `isMinifyEnabled = true`, `isShrinkResources = true`, `proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")`; `perf` inherits through its existing `initWith(getByName("release"))`. `proguard-rules.pro` starts empty except a header, and gains a rule only when a device run shows the need, each with a comment naming the code path. The plugin's `nonMinifiedRelease` variant (generation) forces minification off itself, so profiles are generated against readable names; AGP/R8 rewrite the committed rules to the obfuscated names when building the shrunk variants, so the committed text stays human-readable and the coverage check reads real names.
- **What the stack brings**: Metro embeds its own rules in the runtime artifact (its changelog notes the removal of `-checkdiscard` rules from the embedded set); Room ships consumer rules in its AAR; `proguard-android-optimize.txt` keeps classes with `native` methods and their names (the JNI symbols of the engine bridge); AAPT keeps every manifest-declared component (`MainActivity`, `MetronomeForegroundService`, the profile installer's initialisation provider); Compose Multiplatform resources on Android are static accessors over assets and need no rule; resource shrinking touches only Android `res/` (launcher icons), not `composeResources`. kotlinx.serialization is used for the project document and navigation keys — whether the current version ships its rules inside the artifact is *to verify in implementation* (quickstart §3 opens every destination on the shrunk build; a failure there is answered by the documented serialization keep rules).
- **Why now**: the startup profile's DEX layout is R8-only (AGP ≥ 8.3 performs it by default when `startup-prof.txt` is present and minification is on); without R8 the startup profile would be dormant. Shrinking also reduces the installed size (SC-007) and the 007 measurement build measures the shrunk app from now on, so rounds exercise it on every session.
- **Verification**: one round on the shrunk `perf` build (all four journeys), screenshots of every primary destination at compact (Pixel) and expanded (tablet emulator) widths compared with the debug build, and the instrumented tests of `:androidApp` remain on debug (unchanged). Shrinker warnings are treated like compiler warnings (zero).
- **Alternatives rejected by the owner**: committing the startup profile dormant (no R8); R8 without shrinking/obfuscation only for layout (undocumented, unverified gain).

## D4. `androidx.profileinstaller:profileinstaller:1.4.1` in the app

- **Decision**: add the `implementation` dependency to `:androidApp`. It installs the shipped profile into the device's profile directory on the first launch (so direct `adb install`s benefit, FR-006, not only store installs that carry the profile at install time), and it is what `CompilationMode.Partial(BaselineProfileMode.Require)` relies on (the Macrobenchmark library broadcasts to its `ProfileInstallReceiver`). 1.4.1 is the newest release on Google's Maven (no pre-release beyond it).
- **Effect on debug**: the dependency is present in every variant; it does nothing measurable in debug (profiles are not used by debuggable apps) and adds one manifest-merged initialisation provider. "The debug build contains no profile step" holds: no profile is generated, merged or compiled for it.

## D5. Verification on a device: the installer's broadcast, a forced optimisation pass, `dumpsys`

- **Decision**: `tracepulse profile verify --device <id> [--apk <path>]` installs the given (or freshly built) release-like APK fresh, launches the app once, waits for the installer's first-launch write (the library writes after the first frame; the step waits a few seconds), then: (1) broadcasts `androidx.profileinstaller.action.INSTALL_PROFILE` to `audio.tembra.app/androidx.profileinstaller.ProfileInstallReceiver` and reads the broadcast result (`1` installed, `2` already installed, `6` no profile in the APK, other codes are errors) — this is the "recognised" check; (2) runs `cmd package compile -r bg-dexopt audio.tembra.app` — the device's optimisation pass, triggered immediately; (3) reads `dumpsys package dexopt` for the package and expects `status=speed-profile` — the "optimised from the profile" check. It also confirms `assets/dexopt/baseline.prof` exists in the APK and reports its size (the ≤ 3 % budget, FR-013). The same steps are documented as plain `adb` commands for a maintainer without the pipeline.
- **Alternatives considered**: `ProfileVerifier.getCompilationStatusAsync()` inside the app — needs app code and a way to read the result out (a log line); the `adb` path needs no app change and reads the system's own status. It may be added later to the devtools pane if a maintainer wants it in-app.

## D6. The comparison is a `tracepulse` sibling of `run`, with the pipeline's statistics, never its history

- **Decision**: `tracepulse profile compare --device <id> [--with-full] [--iterations N] [--journeys …] [--no-build --apk … --test-apk …]`. Steps: the full device protocol (`doctor`, exit 2 on refusal) → build `assemblePerf` for the app and the test module with `-Ptembra.perf=true` (same artifacts as a round; `--no-build` accepts prebuilt ones as `run` does) → per state in order `none`, `profile` (and `full` on request): uninstall, install fresh, one `am instrument -e class audio.tembra.perf.ProfileComparisonBenchmark -e tembra.compare.state <state> -e androidx.benchmark.iterations N`, pull `benchmarkData.json` → medians per metric and state, percentage change `profile` vs `none` labelled by the catalogue's direction, Mann–Whitney U on the per-iteration samples at α = 0.01 (the detector's confirmation test, `scipy.stats.mannwhitneyu`), and, with `full`, the share of the `none`→`full` gap closed by `profile` → `app/perf/data/comparisons/<id>/comparison.json` (schema `contracts/comparison.schema.json`) and `comparison.md` (the table pasted into the pull request). Exit statuses: 0 done (whatever the numbers), 2 refused, 3 failed (a state did not complete), 4 usage. Nothing is written to `tracepulse.db`, the records directory or the history branch.
- **Rationale**: reuses `orchestrate_android` (checks, build, install, instrument, pull), `collect_android` key classification, and the detector's test; the comparison id reuses the round-id shape so artefacts sit next to rounds. Default states take about 30 minutes on the Pixel 6 Pro (SC-004 ≤ 40); `full` is optional because it adds roughly 12 minutes and is only context.

## D7. Generation is a `tracepulse` command around the plugin's Gradle task, with device rules and a restore-on-failure

- **Decision**: `tracepulse profile generate --device <id>`: the device protocol (`doctor`) plus an eligibility check (`ro.build.version.sdk` ≥ 33: non-rooted devices can generate profiles from API 33; the Pixel 6 Pro reports API 37) → back up the two committed files → `./gradlew -Ptembra.perf=true :androidApp:generateBaselineProfile` with `ANDROID_SERIAL=<serial>` in the environment so AGP's connected-device provider uses exactly that device (two attached devices and no `--device` is refused by the registry lookup, as for `run`) → run the coverage check (`./gradlew :androidApp:testDebugUnitTest --tests "*BaselineProfileCoverageTest"`) → on any failure restore the backups and exit 3 (2 for a refused check, 4 for usage). The command never touches the history or the report.
- **Rationale**: FR-004's rules are the pipeline's existing checks; `ANDROID_SERIAL` is honoured by AGP's device provider; invoking the coverage test is one implementation of the coverage rule for both the lane and the generator. Expected device time: about 10 minutes (startup collect plus three journeys, up to 15 iterations each until stable), within SC-003 — measured: 3 minutes on the Pixel 6 Pro. *Added in implementation*: the command enforces and restores the measurement state a round enforces (airplane mode, refresh-rate pin, screen on; `device_state.py`), clears the device's test-output directory before the task so stale dated files are never merged, and the coverage test task declares the rule file and the profile as inputs so Gradle re-runs it when either changes (it came from the cache otherwise).
- **Alternatives considered**: a plain documented Gradle command — no device rules, no restore, no exit statuses; a Gradle-managed emulator — an AOSP/ATD system image download and a second code path; left to a later need.

## D8. Coverage rule as one text file read by one JVM test, run in the host lane

- **Decision**: `app/androidApp/baseline-profile-coverage.txt` lists `<label> <class descriptor>` lines: the startup path (`Laudio/tembra/android/TembraApplication;`, `Laudio/tembra/android/MainActivity;`, `Laudio/tembra/ui/navigation/NavigationShellKt;`) and the primary destinations the journeys visit (`Laudio/tembra/ui/home/HomeScreenKt;`, `Laudio/tembra/ui/tuner/TunerScreenKt;`, `Laudio/tembra/ui/metronome/MetronomeScreenKt;`). Amended 2026-10-17: Home was removed and Timeline became the start destination, so the `home` rule became `timeline Laudio/tembra/ui/timeline/TimelineScreenKt;` and the profiles are regenerated with that change (FR-012). `BaselineProfileCoverageTest` (JVM, `app/androidApp/src/test/kotlin/audio/tembra/android/`) reads both files relative to the module directory and fails naming every descriptor that has no rule in `baseline-prof.txt`, or when the profile is missing or empty. The `tembra.android.app` convention plugin registers `checkAndroidHost` → `testDebugUnitTest`, and the root lane adds `:androidApp:checkAndroidHost`.
- **Rationale**: one rule file (like `perf-catalogue.txt`), one check, used by the lane and the generator (D7); descriptors are what the profile format uses, so the test needs no reflection or Android runtime. The spec's "extra coverage never fails" holds because the test only asserts presence.
- **Lane cost**: `testDebugUnitTest` on `:androidApp` compiles the app's debug classes once (cached afterwards); measured against the 5 % budget (SC-006). Fallback: a Gradle verification task with the same logic in `build-logic`.

## D9. Build fails without a committed profile, only for the shipping variants

- **Decision**: a small task `checkBaselineProfileCommitted` in `:androidApp`'s build script fails when `src/main/generated/baselineProfiles/baseline-prof.txt` is missing or empty, with the message "run `uv run tracepulse profile generate --device <id>` from app/perf". It is wired with `androidComponents.onVariants` as a dependency of `merge<Variant>ArtProfile` for the `release` and `perf` build types only — never for `nonMinifiedRelease` (the generation build must succeed before a profile exists) and never for debug.

## D10. What the rounds and the history see

- **Decision**: unchanged commands, unchanged compilation mode (`CompilationMode.Full()` in the four benchmark classes). The `perf` build now carries the profile and is shrunk; a round under full compilation does not exercise the profile, so timing series move only through shrinking (less code to load and verify) — expected as an improvement or no change, flagged in the report as an improvement if the detector sees a step; app size decreases. Recorded in the spec (FR-010, SC-008).

## D11. Documentation and the standing rule

- **Decision**: `app/perf/README.md` gains a "Baseline profiles" section (what they are, the three commands, where the files live, when to regenerate — the startup path, a destination, a journey or a main interaction changed, or before a release — when to commit, the verification steps as plain `adb`, the comparison file, the shrinking rules file and how to add a keep rule); its "Every feature instruments itself" section gains the regeneration sentence (FR-012). `app/README.md`'s "where does X go" table gets a row for the profile files and the coverage rule; `CLAUDE.md`'s command list gets one line for the three commands.

## D12. Lane and build timing baselines

- **Decision**: before any change, record wall-clock times from a warm daemon for `./gradlew checkAndroidHost`, `./gradlew :androidApp:assembleDebug` and `./gradlew :androidApp:assembleRelease` (three runs each, median), and the Pixel 6 Pro round time from the last 007 session; the same measurements after the feature are the evidence for SC-006/SC-007/SC-008. Shrinking makes `assembleRelease` slower (R8) — that is the release build, not the default (debug) build the criterion covers; the number is recorded anyway.
