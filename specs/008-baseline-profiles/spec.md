**Status**: Draft

## Clarifications

### Session 2026-10-12

- Q: What should the performance rounds measure from now on, given that today they measure the fully optimised state, which never shows a profile's effect? → A: Keep the two apart. The rounds stay as they are (fully optimised state) and never run or generate baseline profiles; the profile tooling (generation, comparison) is separate from the performance tests, and the profile's benefit is proven by the separate comparison. Profiles are regenerated when they are needed (covered code changed) or according to best practice (before a release), never as part of a round.
- Q (planning input): The startup profile can only arrange the app's startup code when the release build is shrunk, and the release build does not shrink today; keep the startup profile dormant, or shrink? → A: Shrink. Release-like Android builds (release and the measurement build) are shrunk and obfuscated in this feature (code and resources), with the keep rules the stack needs, so the startup profile takes effect; the shrunk build is verified on a device and by screenshots before it is accepted. Shrinking therefore leaves the out-of-scope list; the debug build and the iOS app stay unchanged.

## User Scenarios & Testing *(mandatory)*

On Android, a freshly installed app runs its code un-optimised until the device has watched it being used for a while; the first launches and the first visit to each screen pay that cost as a slower start and dropped frames. A **baseline profile** is a list, shipped inside the app, of the code paths that matter most: startup, the primary screens and the interactions on them. The device optimises those paths when the app is installed, so the app is fast from its first launch instead of its tenth. A **startup profile** is the part of that list that lets the build place the code used during startup together, so less of the app has to be read before the first frame.

The user of this feature is a Tembra Audio maintainer; the beneficiaries are Android users on their first launches of every build. The profile is generated by running the app's existing benchmark journeys (feature 007), is committed to the repository as a reviewable text file, ships in every release-like Android build, and its benefit is proven with the performance pipeline on real devices. iOS is compiled ahead of time already and has no equivalent; this feature does not change the iOS app.

### User Story 1 - Generate the profile from the app's journeys with one command (Priority: P1)

A maintainer connects a Pixel over USB and runs one command from the repository. The command installs a profile-generation build of the app fresh, drives the same journeys the performance rounds use (cold startup, tuner, metronome, stress), repeats them enough times to produce a stable profile, and writes a baseline profile and a startup profile into the app's source tree at a fixed, documented location. The files are plain text, reviewable in a pull request, and are committed with the feature.

**Why this priority**: nothing else in the feature exists without a generated profile; generating it from the journeys that are already maintained means the profile covers exactly what the pipeline measures and that later features extend it by the rule they already follow (every feature instruments itself).

**Independent Test**: on a fresh checkout with a Pixel attached, run the generation command; the two profile files appear at the documented location, are non-empty, and name the app's own startup path and the screens the journeys visit. Delivers a profile the app can ship.

**Acceptance Scenarios**:

1. **Given** an eligible Pixel attached, awake and unlocked, **When** the maintainer runs the generation command, **Then** the command builds and installs the profile-generation build fresh, runs every generation journey the configured number of times, merges the results, writes the baseline profile and the startup profile to the documented location, and exits successfully without any interactive step.
2. **Given** generation has completed, **When** the maintainer reads the baseline profile, **Then** it lists the app's own code for the startup path (application start, the first screen, the navigation shell) and for every primary destination the journeys visit (Timeline, Tuner, Metronome; Home in Timeline's place until Home was removed from the app on 2026-10-17 and Timeline became the first screen), in addition to any framework code the journeys exercise; a profile that names only framework code is a failed generation.
3. **Given** a journey fails during generation (an anchor is missing, the app crashes), **When** the command runs, **Then** the committed profile files are left untouched, the failure and the journey are named in the output, and the command exits with a failure status.
4. **Given** no device is attached, or two Android devices are attached and none is named, **When** the maintainer runs the generation command, **Then** it fails fast or refuses to guess, exactly as the round command does.
5. **Given** an attached device that cannot generate profiles (its operating system is too old for the facility), **When** the maintainer runs the command, **Then** it refuses before building and names the requirement.
6. **Given** the generation command is run twice on the same build, **When** the two results are compared, **Then** they cover the same startup path and the same screens; differences are limited to ordering and to code reached by timing, so regeneration on an unchanged app never needs to be committed.

### User Story 2 - Ship the profile in the Android app (Priority: P2)

Every release-like Android build (the release build and the measurement build the rounds use) carries the committed baseline profile and startup profile. Those builds are shrunk and obfuscated (unused code and resources removed, names shortened) so that the startup profile can arrange the app's startup code together and the app is smaller; every screen keeps working, which is verified on a device and by screenshots. When the app is installed — from a store or directly from a build, which is how the pipeline and the developers install it — the device picks the profile up on the first launch and optimises the app from it. A maintainer can verify on a device that the profile was picked up and, after the device's optimisation pass, that the app is running optimised from it. The debug build is unchanged. Building the app never requires a device: the committed profile is what the build uses.

**Why this priority**: the shipped profile is the user-facing value of the feature; it depends only on a committed profile existing (Story 1).

**Independent Test**: build the release app, install it directly on a Pixel, launch it once, run the verification step; it reports the shipped profile recognised, and after the optimisation pass it reports the app optimised from the profile. Build the debug app; nothing about it changed. Delivers a faster first launch to users.

**Acceptance Scenarios**:

1. **Given** the committed profile, **When** the release build is produced, **Then** the installed app carries the baseline profile and the startup profile, and the startup profile has been used to arrange the app's startup code together.
2. **Given** the measurement build used by the performance rounds, **When** it is produced, **Then** it carries the same profile as the release build, so a round measures what users receive.
3. **Given** the app installed directly from a build (not from a store), **When** it is launched for the first time, **Then** the device recognises the shipped profile; **When** the device's optimisation pass has run (the maintainer can trigger it immediately), **Then** the verification step reports the app optimised from the shipped profile.
4. **Given** a fresh checkout with no device attached, **When** the app is built, **Then** the build succeeds using the committed profile and never attempts to generate one.
5. **Given** the debug build, **When** it is produced, **Then** it contains no profile step and its build time is unchanged.
6. **Given** the release-like build is shrunk and carries the profile, **When** the installed app's size is measured by the pipeline's app-size family, **Then** it is smaller than in the round before this feature, and the profile itself accounts for no more than 3 % of the installed size.
7. **Given** the shrunk release-like build installed on a Pixel, **When** the four journeys are run on it and every primary destination (Timeline, Tuner, Effects, Pads, Projects, Metronome, Profile; Home too until it was removed on 2026-10-17) is opened at compact and expanded widths, **Then** every journey completes and every destination renders as it does in the debug build, with no missing text, resource or sound and no crash.

### User Story 3 - Prove that the profile helps (Priority: P3)

A maintainer runs one comparison command against a Pixel. It measures the same build in two states, installed fresh for each: with no profile applied, and with the shipped profile applied; on request it adds the fully optimised state as a reference for how close the profile gets to the best case. For each state it runs the pipeline's journeys the configured number of times (20 by default) and writes a comparison: for every metric, the median in each state, the change in percent and whether the difference is statistically confirmed. The comparison is informational: the command succeeds whether or not the profile helped, the result is stored with the raw artefacts outside version control, and its summary is part of this feature's pull-request evidence. The comparison is a separate tool from the performance rounds: a round never runs it, and it never writes into the rounds' history. After the feature merges, the standing labelled session on each Pixel confirms that the rounds themselves are unchanged.

**Why this priority**: the owner asked for proof, not a promise; the comparison is the proof. It depends on Stories 1 and 2.

**Independent Test**: with a Pixel attached, run the comparison command on the current build; a comparison file appears with per-metric medians for both states, the startup first-frame median is lower with the profile by at least the floor in SC-001, and the difference is confirmed. Delivers the "do profiles help this app, and by how much" answer in one file.

**Acceptance Scenarios**:

1. **Given** a Pixel attached that passes the pipeline's device checks, **When** the maintainer runs the comparison command, **Then** it installs the same build fresh for each state, runs every journey the configured number of times in the no-profile state and in the shipped-profile state, and writes a comparison file with, per metric, the median of each state, the change in percent (with its direction labelled better or worse) and the statistical verdict; the command exits successfully regardless of the outcome.
2. **Given** the comparison is run with the reference state requested, **When** it completes, **Then** the fully optimised state appears as a third column, and the comparison states how much of the gap between no profile and full optimisation the shipped profile closes.
3. **Given** a comparison has been written, **When** the device's history is rebuilt and the report regenerated, **Then** no comparison value appears in any series: the comparison never enters the history.
4. **Given** the feature has merged, **When** the maintainer runs a labelled session of rounds on each available Pixel with this feature's label, **Then** the session runs exactly as before this feature (no profile generation, no comparison, the same journeys and optimisation state), the report shows the rounds under that label, no family is flagged above its gate limit in the worse direction, the timing families show no onset at the label boundary, and the app-size family stays within the 3 % budget.
5. **Given** a device check fails (too warm, battery low, network on), **When** the comparison command runs, **Then** it refuses before measuring and names the check, exactly as a round does.

### User Story 4 - Keep the profile current as features land (Priority: P4)

The host test lane checks that the committed profile exists and covers the app's startup path and every primary destination the journeys visit. A later feature that adds a primary destination, a journey or a main interaction regenerates the profile in the same feature, and the repository documentation states this as part of the standing "every feature instruments itself" rule. A feature that forgets is caught by the check, not by a slow first launch in a user's hands.

**Why this priority**: a profile that is not maintained decays silently into no profile; the check and the rule keep Story 2's benefit alive after this feature. It depends on Story 1's committed profile.

**Independent Test**: run the host test lane; the coverage check passes on the committed profile. Remove one destination from the committed profile and run the lane again; the check fails naming that destination. Delivers a profile that cannot silently go stale.

**Acceptance Scenarios**:

1. **Given** the committed profile, **When** the host test lane runs, **Then** the coverage check passes, and the lane's duration is within 5 % of its duration before this feature.
2. **Given** a primary destination added to the app without regenerating the profile, **When** the host test lane runs, **Then** the coverage check fails and names the uncovered destination.
3. **Given** the repository documentation, **When** a maintainer reads the performance pipeline's "every feature instruments itself" section, **Then** it states that a feature which adds a destination, a journey or a main interaction regenerates the profile in the same feature, and it states how (the generation command) and when the regenerated file must be committed (when covered code changed, not for noise-only differences).
4. **Given** the committed profile is empty or missing, **When** a release-like build is produced, **Then** the build fails with a message pointing at the generation command rather than silently shipping without a profile.

### Edge Cases

- The generating device disconnects mid-journey: generation fails with the reason, the committed profile is untouched, and the artefacts collected so far are kept for inspection.
- The device is locked or asleep when generation or the comparison starts: the command refuses with that reason rather than timing out silently.
- The device has already optimised the app from earlier use: both generation and the comparison install the build fresh and reset the app's optimisation state for every state they measure, so an earlier install never leaks into a measurement.
- A journey reaches a screen that is not a primary destination (a dialog, a sheet): the code it exercises is included in the profile as a consequence of the journey; the coverage check requires only the startup path and the primary destinations and never fails for extra coverage.
- The profile names code that no longer exists after a refactor: the build still succeeds (the profile is advisory), the stale entries are ignored at install, and the coverage check decides whether what matters is still covered.
- The comparison shows no confirmed difference, or a worse result, for some metric: the comparison reports it as such; the command still succeeds, and the finding is recorded in the feature's evidence rather than hidden.
- The profile exceeds its share of the size budget: the maintainer reviews what the journeys pulled in; the app-size family in the report shows the overall effect through the existing gate.
- A screen or sound works in the debug build but not in the shrunk build (a keep rule is missing): the journey run or the screenshot check catches it before acceptance; the fix is a keep rule for that code path, never disabling shrinking for the build.
- Generation is run on a device with a different operating-system version than the one the comparison uses: the profile is a list of code paths and is valid on any device; the operating-system fingerprint is recorded on the rounds and the comparison as it is today.
- Two profile generations are started on the same device at once: the second refuses to start while the first holds the device, as rounds do.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The repository MUST provide one command that generates the Android baseline profile and startup profile against a named USB-connected device: a fresh install of a profile-generation build, every generation journey run the configured number of times, the results merged, and the two profile files written to a fixed, documented location in the app's source tree as plain text.
- **FR-002**: The generation journeys MUST be the performance pipeline's journeys (cold startup, tuner, metronome, stress) driven by the same journey definitions and anchors; a journey added to the pipeline later MUST become a generation journey without a second definition.
- **FR-003**: The generated baseline profile MUST cover the app's own code for the startup path (application start, the first screen, the navigation shell) and for every primary destination the journeys visit; a generation whose result does not MUST fail rather than overwrite the committed profile.
- **FR-004**: The generation command MUST be non-interactive, MUST apply the pipeline's device rules (fail fast with no device, refuse with two devices and none named, refuse a locked or asleep device, refuse a device whose operating system cannot generate profiles, name the failed check), MUST leave the committed profile untouched on any failure, and MUST signal success, refusal and failure through distinct exit statuses.
- **FR-005**: The committed baseline profile and startup profile MUST be carried by every release-like Android build (the release build and the measurement build used by the rounds) and MUST NOT affect the debug build; the startup profile MUST be used to arrange the app's startup code together in those builds.
- **FR-005a**: Release-like Android builds MUST be shrunk and obfuscated (unused code and resources removed, names shortened), with the keep rules the app's stack needs so that every screen, sound, resource, persisted preference and the engine bridge keep working; the debug build MUST stay unshrunk. Before the feature is accepted, the shrunk build MUST be verified on a Pixel by running the four journeys on it and by screenshots of every primary destination at compact and expanded widths (added 2026-10-12 from the planning input).
- **FR-006**: The profile MUST take effect when the app is installed directly from a build, not only when installed from a store; a build with an empty or missing committed profile MUST fail with a message that points at the generation command.
- **FR-007**: The repository MUST document a verification step that reports, for an installed app on a device, whether the shipped profile was recognised at first launch and whether the app has been optimised from it, and how to trigger the device's optimisation pass immediately.
- **FR-008**: The repository MUST provide one comparison command that measures one build on one named device in two states installed fresh for each — no profile applied, shipped profile applied — with the fully optimised state available as an optional third reference; each state runs the pipeline's journeys for the configured number of iterations (20 by default), under the pipeline's device checks, and the command writes a comparison file with, per metric, the median of each state, the change in percent labelled better or worse, the statistical verdict using the pipeline's confirmation test, and, when the reference state was measured, the share of the no-profile-to-fully-optimised gap the shipped profile closes.
- **FR-009**: The comparison MUST be informational: it MUST exit successfully regardless of the measured outcome, MUST store its file and raw artefacts outside version control alongside the rounds' raw artefacts, and MUST NOT write any value into the device history or the report series.
- **FR-010**: Performance rounds MUST be unchanged by this feature: they keep measuring the fully optimised state, they MUST NOT generate a profile, and neither the round command nor the labelled session MUST depend on, invoke or be invoked by the profile tooling. The profile's effect on timing is measured only by the comparison command (FR-008). The measurement build still carries the committed profile because it is a release-like build (FR-005), and it is shrunk like the release build (FR-005a); under full optimisation the profile changes none of a round's timing values, so any change a round shows at this feature's label comes from shrinking (a smaller app; possibly a faster start) and MUST be an improvement, never a regression.
- **FR-011**: The host test lane MUST include a coverage check that fails when the committed baseline profile is missing or empty, or does not cover the startup path or any primary destination the journeys visit, naming what is uncovered; the check MUST pass on the committed profile and MUST NOT need a device.
- **FR-012**: The repository documentation MUST state how to generate and regenerate the profile, where the files live, when to regenerate (when the startup path, a primary destination, a journey or a main interaction changes, and before a release), when a regenerated profile is committed (when covered code changed; not for noise-only differences), that regeneration is never part of a performance round, how to run the comparison and read its file, how to verify the profile on a device, and MUST extend the performance pipeline's standing "every feature instruments itself" rule with: a feature that adds a primary destination, a journey or a main interaction regenerates the profile in the same feature.
- **FR-013**: The default build, the existing test lanes and their durations MUST be unaffected by the generation and comparison tooling (within 5 %); zero compiler warnings remains a gate (shrinker warnings count); the installed release-like app MUST be smaller than before this feature, and the profile it carries MUST account for no more than 3 % of the installed size.
- **FR-014**: This feature MUST NOT change the iOS app or the behaviour of shared code; its only app changes are what the Android app needs to carry and apply the profile and to be shrunk (FR-005a). It adds no journeys, sections or counters and changes nothing a round does; it is measured, after it merges, with the standing labelled session on each available Pixel under its own label, which may show improvements from shrinking and MUST show no regression.

### Performance instrumentation declared by this feature

- Journeys added: none. The four existing journeys (startup, tuner, metronome, stress) are reused by the profile-generation command and by the comparison command, which are separate tools from the round command and are never run by it.
- Sections and counters added: none.
- Series affected: the app-size family on the Android devices (a decrease, from shrinking); the timing families may improve because the shrunk app loads less code (rounds keep measuring the fully optimised state, FR-010, so the profile itself moves none of them). No family may regress.
- Labelled session after merge: `baseline-profiles` on the Pixel 6 Pro and the Pixel 7 Pro (five rounds each), run exactly as for any other feature. The iOS build is unchanged by this feature; no iOS session is owed.

### Key Entities

- **Baseline profile**: the committed, human-readable list of the app's hot code paths (startup path, primary destinations, their interactions) that ships inside release-like Android builds; the unit the coverage check reads.
- **Startup profile**: the committed list of the code used during startup, used by the build to arrange that code together; generated and committed with the baseline profile.
- **Generation run**: one execution of the generation command on one device: build identity, device identity and fingerprint, journeys and repetitions, outcome (succeeded, refused, failed with reason), and the resulting profile files.
- **Optimisation state**: the state an installed app is measured in — no profile, shipped profile, fully optimised — always entered from a fresh install.
- **Comparison**: the result of one comparison command on one device: build identity, device identity and fingerprint, the states measured, and per metric the median of each state, the percentage change with direction, the statistical verdict and, when measured, the gap share closed; stored outside version control and never part of the history.
- **Coverage rule**: the list of what the committed baseline profile must cover (the startup path and every primary destination the journeys visit); the only input of the coverage check.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On the Pixel 6 Pro, the cold-startup first-frame median with the shipped profile is at least 15 % lower than with no profile, for the same build installed fresh in each state, over 20 iterations per state, with the difference statistically confirmed by the pipeline's test.
- **SC-002**: Under the same conditions, the cold-startup time-to-full-display median is lower with the shipped profile, statistically confirmed, and the first-open sections already measured by the tuner and metronome journeys are each lower, statistically confirmed; no metric of any journey is worse with the profile in a statistically confirmed way.
- **SC-003**: From a fresh checkout with a Pixel attached, a maintainer generates the profile with one command and no interactive step in 15 minutes of device time or less, and the result passes the coverage check without edits.
- **SC-004**: The comparison command produces its file with one command and no interactive step in 40 minutes of device time or less for the two default states.
- **SC-005**: On a Pixel after a direct install and one launch, the verification step reports the shipped profile recognised; after the maintainer triggers the optimisation pass it reports the app optimised from the profile, within two minutes of the install.
- **SC-006**: The coverage check passes on the committed profile, and fails naming the destination when any one primary destination is removed from the profile, inside the host test lane's existing duration (within 5 %).
- **SC-007**: The installed release-like app is smaller than in the round before this feature, as measured by the pipeline's app-size family, and the profile it carries is at most 3 % of the installed size; the default build and the existing test lanes complete within 5 % of their earlier durations with zero new warnings; the debug build time is unchanged.
- **SC-008**: After the feature merges, a labelled session of five rounds on each available Pixel completes without an interactive step in the same device time as before this feature (within 5 %), no family is flagged above its gate limit in the worse direction, and every onset at the label boundary is an improvement.
- **SC-009**: The feature's pull request carries the comparison summary for the Pixel 6 Pro, the labelled-session report and the screenshots of the shrunk build, so the gain is on record with the change that produced it.
- **SC-010**: On the shrunk release-like build installed on the Pixel 6 Pro, one performance round succeeds (all four journeys complete) and every primary destination renders at compact and expanded widths with no missing text, resource or sound, verified by screenshots compared with the debug build.

## Assumptions

- This feature is Android-only. iOS builds are compiled ahead of time and have no equivalent of a baseline profile; the iOS app, its journeys and its series are unchanged, and no iOS session is required after the merge.
- The owner's Pixel 6 Pro (the one attached today) and Pixel 7 Pro are the generation and comparison devices; both run operating-system versions that allow profile generation without special device access. Generation on an emulator is a technology choice left to the plan; the specification requires only that a USB-connected Pixel works.
- The profile files are committed to the repository and reviewed like code; the build uses the committed files and never generates them. Regeneration is on demand: when covered code changes (a new destination, journey or main interaction) and before a release, following common practice for shipped profiles; it is never part of a performance round, and noise-only differences from regenerating an unchanged app are not committed.
- The performance pipeline and the profile tooling are kept apart (clarified 2026-10-12): the round command and the labelled session are untouched, keep measuring the fully optimised state, and never generate or evaluate a profile; the generation and comparison commands are separate entries that reuse the pipeline's journeys and device checks but write nothing into its history.
- The 15 % floor in SC-001 is the project's expectation for an app of this shape (a small shared-UI app with a navigation shell and two instrument screens) based on published results for apps that ship a baseline profile; the comparison records the actual figure whatever it is, and a result below the floor is a finding to document, not a reason to hide the comparison.
- The comparison reuses the pipeline's journeys, anchors, device checks, iteration count and statistical test; it is a sibling of the round command, not a new pipeline. Its raw artefacts live where the rounds' raw artefacts live.
- The "fully optimised" reference state in the comparison is the state the rounds measure today; measuring it is optional in the comparison because it roughly doubles the device time and is only context for the profile's gain.
- Framework code that the app's UI framework and libraries already describe in their own profiles is merged into the shipped profile automatically; this feature is responsible for the app's own code paths.
- This feature is tooling and build work: under the constitution's "every feature instruments itself" rule it adds no journeys or sections. The labelled session after it merges is the standing cadence applied to every feature, not a measurement of the profile; it is expected to show no change in the timing families, and the profile's gain is on record through the comparison instead.
- The constitution's build order is unchanged; the audio spine remains the next product feature.
- Shrinking and obfuscating the release-like Android builds is in scope by the owner's decision of 2026-10-12 (planning input): it is what lets the startup profile arrange the startup code, and it makes the app smaller. The keep rules are limited to what the stack needs; the shrunk build is accepted only after the four journeys run on it and every primary destination is screenshot-verified at compact and expanded widths.
- Out of scope: store-delivered profiles and any store distribution, profiles for the iOS app, changing the pipeline's detector or gate parameters, and continuous-integration wiring for generation or comparison (both commands are shaped so a CI job can call them unchanged later, as the round command is).
