# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tembra Audio is a free, open-source mobile DAW for Android and iOS: a Kotlin Multiplatform control plane and Compose Multiplatform UI on top of one shared C++ real-time audio engine (Oboe on Android, AVAudioEngine/RemoteIO on iOS).

**Application code lives in `app/`** (Gradle root; scaffold landed with feature 001 on 2026-09-24). Modules: `:shared:core` (pure domain), `:shared:engine` (`AudioEngine` facade over the C++ engine: JNI on Android, cinterop on iOS), `:shared:data` (persistence), `:shared:ui` (Compose Multiplatform screens, ViewModels, theme, Metro graph, navigation shell (Navigation 3), design-system chrome components, debug-only devtools; iOS framework `TembraShared`), `:androidApp`, `iosApp/` (Xcode), `engine/` (CMake C++ core, `include/tembra_engine.h` is the C ABI), `:engine:android` (CMake/NDK + Prefab Oboe build helper). Module map and "where does X go" table: `app/README.md`.

Commands (run from `app/`, Gradle wrapper 9.7.0; prerequisites in `app/README.md`):

- Build and run Android: `./gradlew :androidApp:installDebug` then `adb shell am start -n com.tembraaudio/audio.tembra.android.MainActivity`
- Build and run iOS: `cd iosApp && xcodebuild -project iosApp.xcodeproj -scheme iosApp -configuration Debug -destination 'platform=iOS Simulator,name=iPhone 18 Pro' -derivedDataPath build build`, then `xcrun simctl install/launch "iPhone 18 Pro" … com.tembraaudio`
- Release builds on every attached target (judge smoothness only on these; debug builds are much slower): `tools/release-android.sh` (`release` type signed with the debug key, baseline profile compiled) and `tools/release-ios.sh` (`Release` configuration, devices and booted simulators); `--help` for options, details in `app/README.md` § Build and run.
- Test lanes: `./gradlew checkAndroidHost` (JVM), `./gradlew checkIos` (simulator), `./gradlew checkAndroidDevice` (connected device), `./gradlew engineHostTest` (C++ Catch2). Compose UI tests live in the `uiTest` source set and run only on the simulator and the device.
- Screenshots: `android screen capture --output <file>`; `xcrun simctl io "<device>" screenshot <file>`
- Desktop windows (feature 011): two Android desktop emulators, one at a time: `Tembra_Desktop_API37` (Android 17 "Desktop (Preview)", primary, `emulator -avd Tembra_Desktop_API37 -port 5582 -gpu host` (a freshly created AVD renders with SwiftShader, which times out the UI tests' pixel captures; `app/README.md` sets `hw.gpu.mode=host` in the AVD's config.ini instead), then `adb -s emulator-5582 shell am switch-user 10` after a cold boot) and `Tembra_Desktop_API34` (Android 14 desktop, 16:9, no touchscreen, port 5580). Run a lane on one of them with `tools/gradlew-device.sh emulator-5582 <gradle arguments…>`; the iPad's desktop behaviour runs in the `TembraDesktopTests` XCUITest scheme on an iPad simulator. Setup: `app/README.md` § Build and run.
- Zero compiler warnings is a gate; run with `--warning-mode all`. CI enforces it with `-Ptembra.warningsAsErrors=true --warning-mode fail`; pass the same flags to reproduce a CI failure locally.
- CI and Renovate: `.github/workflows/ci.yml` (Android host + R8 release build on Linux, with R8's Configuration Analyzer scores on the run page and `configanalyzer.html` as an artifact; `checkIos` + `engineHostTest` on macOS), `.github/workflows/renovate.yml` and `.github/renovate.json5` (weekly grouped updates, merged by Renovate once every check passes). Read `app/README.md` § CI and dependency updates before changing a job, a Renovate group or the pinned androidx Compose lines.
- Performance rounds (feature 007): `cd app/perf && uv sync`, then `uv run tracepulse run --device pixel6|iphone14 --label <feature> [--rounds 5]`, `uv run tracepulse sync && uv run tracepulse report --open`; `uv run pytest` is the pipeline's own suite. From an agent session build the measurement artifacts through `gradle-run` (`./gradlew -Ptembra.perf=true :androidApp:assemblePerf :perf-benchmarks:assemblePerf`) and pass them with `--no-build --apk … --test-apk …`. Commands, exit statuses and the per-feature cadence: `app/perf/README.md`.
- Baseline profiles (feature 008): `cd app/perf && uv run tracepulse profile generate|compare|verify --device pixel6` — generate writes `app/androidApp/src/main/generated/baselineProfiles/` (regenerate when the startup path, a primary destination, a journey or a main interaction changes; commit when covered code changed), compare proves the gain, verify checks an installed build; release-like Android builds are shrunk with R8 and refuse to build without a committed profile. Details: `app/perf/README.md` § Baseline profiles.
- Device runs on one Android target (feature 010): `app/tools/gradlew-device.sh <serial> <gradle arguments…>` runs the wrapper with `ANDROID_SERIAL` set, so `checkAndroidDevice` runs on that device alone while others stay attached.
- Run conditions before any lane, capture or perf round on a physical Android device (owner's rules of 2026-10-25): `app/tools/apply-device-run-conditions.sh <serial>` (screen awake, brightness at its floor, music stream silent, do-not-disturb on; the OPPO refuses the brightness settings, dim it by hand).
- Measure a recorded take's offset to the beat, or the monitoring delay (feature 010, quickstart §8, the one sounding step): `app/tools/measure-take-alignment.py take.wav --bpm 120 [--json]`, `app/tools/measure-take-alignment.py --monitor loopback.wav`.
- Measure the pan law, the opposite side's leakage or a pan sweep's smoothness on loopback recordings (feature 012, quickstart §8, the loopback step): `app/tools/measure-pan-law.py centre.wav left.wav right.wav [--within 0.5] [--floor -60]`, `app/tools/measure-pan-law.py --sweep sweep.wav --hz 440`; its synthetic-file tests run with `python3 -m unittest discover -s app/tools/tests`.
- Add a Material Symbols glyph: `tools/fetch-material-symbols.sh [--fill] <glyph> [<glyph> ...]` (pinned commit, normalised for the Compose resource loader; `--fill` fetches the filled variant as `ic_<glyph>_fill_24.xml`), then add a `TembraIcon` value.
- Regenerate the navigation's hand-drawn Tuner and Metronome glyphs: `tools/make-nav-glyphs.py [--preview <dir>]`
- Google Play testing: every push to `main` that changes the Android app is tested, signed with the upload key (Secret Manager, keyless Workload Identity Federation) and released on the internal testing track (promote to closed testing by hand in Play Console) by `.github/workflows/play-closed-testing.yml`; one-time setup `tools/play/setup-wizard.sh`, script tests `python3 -m unittest discover -s tools/play`, everything else in `docs/google-play-publishing.md`.

## Workflow: spec-kit drives all feature work

The project uses GitHub spec-kit. It was initialised on 2026-09-18 with `uvx --from git+https://github.com/github/spec-kit.git specify init --here --integration claude --script sh` (the old `--ai` flag is gone; re-run the same command with `--force` to refresh templates). The skills live in `.claude/skills/speckit-*/` and are invoked with hyphens: `/speckit-constitution`, `/speckit-specify`, `/speckit-clarify`, `/speckit-plan`, `/speckit-checklist`, `/speckit-tasks`, `/speckit-analyze`, `/speckit-implement`, `/speckit-converge` (not the older dotted `/speckit.*` form). Helper scripts are in `.specify/scripts/bash/`. `specs/` is created by the first `/speckit-specify`.

- `.specify/memory/constitution.md` is the ratified constitution (v1.3.5, ratified 2026-09-19, last amended 2026-11-03): eight principles plus stack constraints and quality gates, seeded from the research briefs below and `docs/research/kmp-code-architecture.md`. It supersedes this file where they disagree; amend it only through `/speckit-constitution`. Since 2026-10-08 every feature after the performance pipeline (007) that adds an interaction or an engine path must ship its own performance instrumentation (sections, anchors, a benchmark journey on both platforms) and be measured with a labelled session after it merges; the spec declares the journeys and sections.
- `specs/<feature>/spec.md` says WHAT (user-facing behaviour); `plan.md` holds technology choices. Keep them apart.
- The first feature is the project scaffold that creates `app/shared`, `app/engine`, `app/androidApp`, `app/iosApp`.
- Build order after that is fixed in the constitution (amended 2026-09-29, 2026-10-13, 2026-10-27 and 2026-11-03): tuner first (microphone capture and reference tones, the first audio in the app), then metronome (a global, standalone metronome for playing along, not part of any recording or timeline session; its sound set and configuration, tempo and bar-shape models and engine click scheduler are reused by transport/timeline, never duplicated), then the audio spine with transport and timeline as one feature (009: the engine + JNI/cinterop bridge playing a multi-clip project, the transport bar, the timeline, import, the Projects library), then recording (010: the microphone as a track source, before the mixer so the input level meter lives on the track header), then large screens and desktop (011: Chromebooks, Googlebooks and Android desktop windows, devices without a touchscreen or a microphone, iPad windows with a keyboard and a trackpad, drag and drop of audio files, the Play presence on those devices; no musical capability, so nothing is pulled forward), then mixer (012), effects + automation, loops + speed, collaboration last. `docs/DAW-App-Research-Report.md` §6 has the rationale for each step; its own order (spine, timeline, mixer, metronome, effects, recording, tuner) is the research proposal, the constitution's is the decision.

## Architecture rules that every spec and plan must respect

These come from `docs/research/` and are the reason the research exists; treat them as settled.

1. **Nothing Kotlin runs on the audio callback.** Kotlin/JVM and Kotlin/Native are garbage collected. The C++ engine owns the real-time thread; Kotlin only produces commands. The two sides talk exclusively through lock-free SPSC FIFOs and atomics. No allocation, locks, I/O or unbounded work inside the callback.
2. **One shared C++ engine, not per-platform DSP.** Exposed to Kotlin through an `expect class AudioEngine` facade with JNI (Android) and cinterop (iOS) actuals. Platform code is a thin I/O shell that must accept a variable frame count per callback at 48 kHz.
3. **Everything musical is stored in beats** (clip starts, automation points, loop positions) and converted to samples through the tempo map at render time.
4. **Permissive licenses only in the shipped binary.** Allowed: Oboe, miniaudio, dr_libs, Signalsmith Stretch, STK, Maximilian, KissFFT/pffft, MWEngine as a pattern. Never link JUCE, Tracktion, Rubber Band, KFR, Superpowered, élastique. LGPL (SoundTouch, libsndfile, FFmpeg) only if unavoidable and dynamically linked. Full table: `docs/research/kmp-architecture-tools.md` §5.

Detailed mechanics for each rule: `docs/research/daw-internals.md` (graph, pan law, PDC, automation smoothing, transport), `docs/research/metronome-design.md`, `docs/research/tuner-algorithms.md`.

**Kotlin-side code architecture** (module graph, presentation pattern, navigation, DI, persistence, testing) is decided in `docs/research/kmp-code-architecture.md`: four shared Gradle modules (`:shared:core`, `:shared:engine`, `:shared:data`, `:shared:ui`) plus thin apps; MVVM with multiplatform `ViewModel` + `StateFlow`; 60–120 Hz telemetry read in the draw phase, never through `StateFlow`; Jetpack Navigation 3 multiplatform with Material 3 adaptive; Metro for DI; Room KMP + DataStore + kotlinx.serialization JSON project files; `kotlin.test` + Turbine + `runComposeUiTest`, C++ tests in Catch2. Plans must follow it or amend it there first. Evidence: `docs/research/kmp-reference-repos.md` (what JetBrains and Google actually ship) and `docs/research/notebooklm-kmp-architecture-qa.md`.

## Things that bite

- `reference/competitor-apps/` is about 720 MB of pulled APKs and extracted `.so` files, git-ignored and not present on a fresh clone. It contains over 8,000 files; scope any repository-wide search or listing to exclude it.
- Diagrams in `docs/diagrams/` have an editable `.excalidraw` beside each `.png`. Edit the source and re-render; do not edit the PNG alone.
- To refresh the Stitch export after design edits, follow the re-pull steps in `design/stitch/README.md` (Stitch project `12040171611712589599`, MCP server `stitch`). Screenshot URLs need the `=s0` suffix or you get 512px thumbnails.
- The iPhone Duo simulator needs Xcode 27.1 (the default `/Applications/Xcode.app`, no `DEVELOPER_DIR`) and an iOS 27.1 simulator runtime (the 27.2 beta runtime refuses the device); poses are Device Hub buttons, not `simctl`, Compose Multiplatform reports no fold posture on iOS, and on the closed Duo held upright the app uses the experimental `LayoutMode.EndRail` and the metronome's Pocket form (gated by `isIphoneDuo`). Setup, fold APIs and Apple's guidance: `docs/research/iphone-duo.md`.
- The NotebookLM notebooks behind the research are listed in `docs/README.md` and can be queried with the `notebooklm` CLI.
- The `perf-history` branch holds the performance round records (`records/<device_id>/<round_id>.json`, one file per round, written by `tracepulse run`); it is append-only: never rebase, rewrite or merge it into `main`. Its worktree lives at `app/perf/.history/` (git-ignored), the derived SQLite cache and the raw traces under `app/perf/data/`, the report under `app/perf/reports/`.
