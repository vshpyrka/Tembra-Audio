# Profiling and performance regression tracking for Tembra Audio (Android + iOS)

**Status:** research, 2026-10-06. Input to a future spec-kit feature (suggested: `007-performance-pipeline`). Nothing here is built yet.
**Written against:** the app at `main` 55835a7 (Kotlin 2.4.20, AGP 9.3.3, Compose Multiplatform 1.12.1), Xcode 26.6 (17F113) on this Mac, trace-pulse at `/Volumes/External/Dev/trace-pulse` (SPEC v2, Phase 4c complete).
**How it was produced:** a NotebookLM deep-research run plus eight targeted questions against a 73-source notebook (`5cecd7ef-85e6-485e-a26d-b38922cb65c5`; raw output in `notebooklm-profiling-report.md` and `notebooklm-profiling-qa.md`), an independent web-research pass over Apple, Google, JetBrains, Perfetto and vendor primary sources (raw output with URLs in `profiling-web-findings.md`), and checks run on this Mac's toolchain. Where the two research streams disagreed, the primary source or the local check wins and the disagreement is noted.

## 1. Summary

- **Android keeps trace-pulse as it is.** Macrobenchmark (startup, frames, memory, trace sections) plus a Perfetto trace per iteration, a fixed device protocol on the Pixels, Skia-exact step fitting with Mann-Whitney/Benjamini-Hochberg confirmation, and the self-contained HTML report. Google's own stance matches it: run benchmarks on physical devices, graph results over time, never decide from one build.
- **iOS gets the same pipeline on Apple's stock tooling, not on Instruments.** `xcodebuild test` runs XCTest performance tests (`measure(metrics:options:block:)` with `XCTApplicationLaunchMetric`, `XCTOSSignpostMetric`, `XCTMemoryMetric`, `XCTCPUMetric`, `XCTClockMetric`, and on iOS 26+ `XCTHitchMetric`), and `xcrun xcresulttool get test-results metrics` returns per-iteration `measurements[]` as JSON (verified on Xcode 26.6, §5.2). That is a direct feed into trace-pulse's `samples` table. `xctrace` (Time Profiler, Allocations, Animation Hitches, Audio System Trace) is the deep-dive and audio-thread tool, scriptable on a USB iPhone, not the series collector.
- **The common interface exists at two levels.** In the app: one tracing facade (`expect`/`actual` in Kotlin, one macro in the C++ engine) that becomes ATrace sections on Android and `os_signpost` intervals on iOS, so the same named section is a `TraceSectionMetric` on Android and an `XCTOSSignpostMetric` on iOS. In the pipeline: trace-pulse's collect layer is the only platform-specific part; store, detect and report are shared.
- **trace-pulse moves into this repository** as an includable module with an `ios` collector, the Android benchmark module de-templated for Tembra, an XCTest performance target in `iosApp`, and the journeys for both platforms kept together (owner's decision, §12).
- **Two CI workflows:** a self-hosted runner on a second Mac with the Pixel and the iPhone on USB (the primary, protocol-controlled series), and a small fixed set of happy-path runs on a cloud device farm. The farm needs a correction to the plan: **Firebase Test Lab is deprecated and shuts down on 2027-09-30**; its successor, Google Cloud's Developer Device Platform, requires billing. Design the farm step as a thin adapter (§9.2).
- **Maestro cannot drive a physical iPhone** (simulators only, per its own docs); it can drive USB Android devices and iOS simulators. It is a smoke-journey tool, not a measurement tool (§9.3).
- **Gate and trend:** the step-fit trend detector remains the signal; a coarse tripwire gate is implemented once in trace-pulse for both platforms, with Xcode `.xcbaselines` optional for local Xcode runs (§6.5).
- **Audio-thread health is the engine's own job.** iOS exposes no public overload counter, so the engine counts over-budget callbacks and xruns itself (Oboe's `getXRunCount` on Android) and publishes them as telemetry; the pipeline turns them into `audio.*` series (§7).

## 2. What exists today

**In the app.** No benchmark module, no XCTest target, no CI workflow, no `ReportDrawn`/`reportFullyDrawn` call, no `enableTraceOSLog()` call, no engine telemetry yet (the audio spine is the next feature; `tembra_engine.h` is still the descriptor-level revision). Compose `Modifier.testTag` is already used in the tuner screens, which is what UiAutomator and XCUITest will target. `docs/research/kmp-code-architecture.md` already decides the pieces this report builds on: telemetry read in the draw phase (never through `StateFlow`), `-Xruntime-logs=gc=info` and `kotlin.native.binary.enableSafepointSignposts=true` in debug builds, a Compose compiler metrics check in CI, and "measure p99 frame time during pinch-zoom on both platforms" as an open question.

**trace-pulse.** A Python 3.9 CLI (`tracepulse init | doctor | run | inject | revert | analyze | report | status | compare`) plus a parameterised `:tracepulse-benchmarks` Gradle module template. Per round: preflight (JDK, SDK, device, battery ≥ 50 %, battery temperature ≤ 35 °C, refresh rate pinned, airplane mode on), build, fresh install, one unmeasured warm-up launch, `StartupBenchmark` (COLD, `StartupTimingMetric`) and `ScrollJankBenchmark` (`FrameTimingMetric` + `MemoryUsageMetric`), 20 iterations each, `am instrument -w`, pull `benchmarkData.json` and one `.perfetto-trace` per iteration, APK size, advisory `dumpsys meminfo`, store to SQLite (`rounds`, `samples`, `aggregates`, `detections`, `artifacts`), detect (Skia step fit, `WIDTH=5`, `THRESHOLD=15`, screening gates, Mann-Whitney 40 v 40 on raw iterations with BH `q=0.05`, status ratchet, APK threshold rule, environment-suspect grouping), render `report.html`. Validated with four injected regressions on three devices (all four confirmed at their onset round on the Galaxy A52; on the two Pixels the frames injection was too weak to confirm, the other three were); measured round-to-round CoV 1–2 % under the protocol. Only `collect.py`, `orchestrate.py`, `traces.py` and the benchmark template are Android-specific.

## 4. Android lane

Nothing changes in principle; the details below are the current state of the standard tools, confirmed against developer.android.com and Perfetto docs during this research.

- **Macrobenchmark 1.5.0** (stable 2026-09-09): `StartupTimingMetric` (`timeToInitialDisplayMs`, `timeToFullDisplayMs`; the latter needs `ReportDrawnWhen`/`ReportDrawnAfter` in Compose, which Tembra does not call yet), `FrameTimingMetric` (`frameDurationCpuMs` P50/P90/P95/P99, `frameOverrunMs` on API 31+, `frameCount`), `TraceSectionMetric(name, Mode)` with `Mode.Sum` as default and mode names embedded in the output name, `MemoryUsageMetric`, `MemoryCountersMetric`, `PowerMetric` (Pixel 6+), `ArtMetric`, custom `TraceMetric`. 1.4.0 added `measureRepeated(perfettoConfig = …)` for custom Perfetto configs and the `benchmark-traceprocessor` session API; `coefficientOfVariation` is in the JSON. Instrumentation arguments worth wiring into `tracepulse.yml`: `androidx.benchmark.profiling.mode = StackSampling` (callstack samples per iteration; whether the backend is simpleperf or `traced_perf` is not stated in the docs), `androidx.benchmark.fullTracing.enable`, `androidx.benchmark.suppressErrors`.
- **Perfetto from C++.** Two options: the NDK ATrace API (`<android/trace.h>`: `ATrace_beginSection`, `ATrace_endSection`, `ATrace_setCounter` since API 29; all under `ATRACE_TAG_APP`, no categories) or the Perfetto SDK (`TRACE_EVENT("cat","name")`, in-process or system backend). ATrace is enough for Tembra: sections show up in Macrobenchmark's `TraceSectionMetric` and counters in trace_processor's counter tables, which trace-pulse's `traces.py` already queries. The SDK is only worth it if we want custom tracks or categories, and it does not help iOS (§6.1).
- **Callstack sampling.** Perfetto's `cpu_profile -n <pkg> -f 100` (`linux.perf` data source; app must be `profileable` or `debuggable`; the current doc lists Android 15+ as the prerequisite, which the Pixels on Android 17 satisfy) and simpleperf's `app_profiler.py` + `report_html.py` (release builds need `<profileable android:shell="true"/>`). Both are scriptable; both are what the installed `android-profiler` skill drives (the `android` CLI itself has no profiler command; profiling is delivered as that skill, which calls Perfetto's `record_android_trace`, `cpu_profile`, `heap_profile`, `java_heap_dump`).
- **Compose compiler reports** work per Kotlin target (`<metricsDestination>/<target>/…`), and `includeTraceMarkers` is on by default, which is why composable names already appear in Android system traces.
- **Field:** Android Vitals (crash/ANR rate, slow rendering, frozen frames, slow launches, population percentiles; Play tracks only) and JankStats (per-frame durations with UI-state annotation, any build). Neither sees the audio thread.

## 5. iOS lane

### 5.1 What Apple's stock command-line tooling gives unattended

Apple documents the pieces; the composition into a series collector is ours.

- **`xcodebuild test -destination 'platform=iOS,id=<udid>' -resultBundlePath X.xcresult [-enablePerformanceTestsDiagnostics YES]`** runs performance XCTests on the USB iPhone. Apple's guidance for stable numbers: Release configuration, "Debug executable" off, code coverage and sanitizers off, real devices rather than simulators. `-test-iterations N` repeats whole tests; it is **not** the `measure` block's iteration count (that is `XCTMeasureOptions.iterationCount`, set in code; a performance test runs the block `iterationCount + 1` times and discards the first). Apple's page does not state the default; set **20** explicitly to match trace-pulse. (NotebookLM answered "10" without a source; treat as unknown.)
- **Metrics** (`XCTMetric` conformers in current docs): `XCTClockMetric` (Clock Monotonic Time), `XCTCPUMetric` (CPU Time, CPU Cycles, CPU Instructions Retired), `XCTMemoryMetric` (Memory Physical, Memory Peak Physical), `XCTStorageMetric`, `XCTApplicationLaunchMetric(waitUntilResponsive:)`, `XCTOSSignpostMetric(subsystem:category:name:)` plus built-ins `navigationTransitionMetric`, `customNavigationTransitionMetric`, `scrollingAndDecelerationMetric`, and `XCTHitchMetric(application:)` (iOS 26+, UI tests only). An `XCTOSSignpostMetric` over an **animation** signpost (`os_signpost(.animationBegin, …)` / `os_signpost_animation_interval_begin`) reports duration plus hitch count, hitch time, hitch time ratio, frame rate and frame count (WWDC20 10077; thresholds there: < 5 ms/s good, 5–10 investigate, ≥ 10 act). On a simulator, signpost metrics yield duration only; the hitch and frame-rate columns need a device.
- **Baselines** live in `<Project>.xcodeproj/xcshareddata/xcbaselines/<TargetUUID>.xcbaseline/` as plists keyed by host Mac model **and** target device (`runDestinationsByUUID`), with per-metric `baselineAverage` and the thresholds `maxPercentRegression`, `maxRegression`, `maxStandardDeviation`, `maxPercentRelativeStandardDeviation`. Apple sets them only through the Xcode GUI and documents the pass rule as "worse than the baseline value by more than the maximum standard deviation". A baseline recorded on one Mac+iPhone pair is silently ignored on another. (Format from a public repository; Apple does not document it.)

### 5.2 Reading the numbers (verified on this Mac, Xcode 26.6)

`xcrun xcresulttool get test-results metrics --path X.xcresult [--test-id <id>] [--compact]` returns JSON (schema 0.1.0):

```
TestWithMetrics { testIdentifier, testIdentifierURL, testRuns[] }
TestRunWithMetrics { testPlanConfiguration{configurationId, configurationName}, device{deviceId, deviceName}, metrics[] }
Metric { displayName, unitOfMeasurement, measurements: [double], identifier, baselineName, baselineAverage,
         maxRegression, maxPercentRegression, maxStandardDeviation, maxPercentRelativeStandardDeviation, polarity }
```

`measurements` is the per-iteration array, so the 40 v 40 Mann-Whitney confirmation works unchanged. `xcrun xcresulttool export metrics --path X.xcresult --output-path DIR` writes the same data as CSV with a `manifest.json`. Both subcommands exist in Xcode 16+; `xcresulttool get object` is deprecated (`--legacy`). This closes the gap that made Firefox iOS keep its XCTMetric runs out of CI in 2021 ("there is not a good way to retrieve the data").

### 5.3 xctrace for deep dives and the audio thread

`xcrun xctrace record --template '<name>' --device <udid> (--launch -- <bundle-id> | --attach <pid|name>) --time-limit 30s --no-prompt --output X.trace`, then `xctrace export --input X.trace --toc` to list tables and `--xpath '/trace-toc/run[@number="1"]/data/table[@schema="…"]'` to export XML. Templates present in Xcode 26.6: Time Profiler, CPU Profiler, Allocations, Leaks, Animation Hitches, App Launch, Audio System Trace, Metal System Trace, System Trace, Power Profiler and others; instruments include Audio Client, Audio Server, Audio Statistics, Hitches, Core Animation FPS, Points of Interest, os_signpost. Apple publishes no web documentation for the Audio System Trace tables, so the export schema names are a spike (§10). Whether the phone must be unlocked and the Mac logged in for `xctrace record --device` is not documented either; your own notes say GUI automation stops when the Mac locks, so treat it as "logged-in session required" until tested.

### 5.4 Kotlin/Native and Compose Multiplatform specifics

- **Symbolication:** the Kotlin/Native compiler emits `.dSYM` for release binaries on Apple platforms by default and Xcode picks them up; Instruments shows Kotlin frames. `-Xadd-light-debug=enable` is documented for non-Apple targets only. `sourceInfoType=coresymbolication` is for exception stack traces, not needed for profiling.
- **GC:** `kotlin.native.binary.gc=cms` is the default since 2.4.0 (we are on 2.4.20); `pmcs`, `stwms`, `noop` exist. `enableSafepointSignposts=true` emits GC pauses as `os_signpost` intervals under subsystem `org.kotlinlang.native.runtime`, category `safepoint`, so a hitch can be attributed to a GC pause in the same Instruments timeline as the Compose frame signposts. `-Xruntime-logs=gc=info` prints to stderr. The default allocator is mmap-based and tagged (VM tag 246, `mmapTag`); Kotlin objects therefore show as tagged VM regions, not as malloc events in the Allocations instrument, unless `disableMmap=true` (inference from the option docs; not tested).
- **Frame production:** Compose Multiplatform on iOS draws through Skia into a `CAMetalLayer` (`MetalRedrawer.ios.kt`), paced by `CADisplayLink`, with `parallelRendering = true` by default (encoding on a render thread). The redrawer already wraps its phases in `trace("MetalRedrawer:draw")`, `…:pictureRecording`, `…:nextDrawable`, `…:encodeAndPresent`, `…:waitTransaction`; after `enableTraceOSLog()` (stable since CMP 1.8.0) these are `os_signpost` intervals visible in Instruments. Tembra does not call `enableTraceOSLog()` yet.
- **JetBrains' own benchmark harness** (`compose-multiplatform/benchmarks/multiplatform`) is the reference pattern for scripting an iPhone from a Mac: `xcrun xctrace list devices` → `xcodebuild build -configuration Release -destination id=<udid>` → `xcrun devicectl device install app` → `xcrun devicectl device process launch --console …` and read JSON from the app's stdout. It measures frame times in-app (`CADisplayLink`, `UIScreen.maximumFramesPerSecond`, `TimeSource.Monotonic`), not with Instruments. If XCTest's hitch ratio turns out too coarse for the timeline work, this self-instrumented path gives per-frame percentiles on iOS with ~100 lines of Kotlin.

## 6. The common interface

### 6.1 App level: one tracing facade

What already exists: `androidx.compose.ui.util.trace(sectionName) { … }` (in `compose.ui:ui-util`, a dependency we already have) is a common `expect` that becomes `android.os.Trace.beginSection` on Android and, after `enableTraceOSLog()`, an `os_signpost` interval on iOS. Its iOS mapping uses one fixed signpost name (`CMPInterval`, log `androidx.compose`/`androidx.compose.ui`) with the section name as the message, so `XCTOSSignpostMetric(subsystem:category:name:)` cannot target one section. `androidx.tracing` 2.0 is JVM+Android only. The Perfetto SDK's in-process backend is documented for Android, Linux, macOS and Windows; the source has an iOS OS define, but nothing documents or tests it. Sentry KMP and Datadog KMP are field monitoring, not a tracing facade.

Decision proposed for the feature:

- **Kotlin:** `audio.tembra.core.perf.trace(name) { }` (name to be settled in the spec) as `expect`/`actual` in `:shared:core`. Android actual: `androidx.tracing.Trace.beginSection/endSection` (and `setCounter` for values). iOS actual: a three-function C shim in the engine's platform layer (`tembra_trace_begin(const char*)`, `tembra_trace_end`, `tembra_trace_counter`) bound through the existing cinterop, because `os_signpost_interval_begin` is a variadic C macro that cinterop cannot bind. The shim logs on `os_log_create("audio.tembra", "<category>")` with the **section name as the signpost name**, so each section is individually measurable with `XCTOSSignpostMetric(subsystem: "audio.tembra", category: "ui", name: "timeline.zoom")` and individually a `TraceSectionMetric("timeline.zoom")` on Android. Call `enableTraceOSLog()` at iOS start-up in perf builds so Compose's own frame phases sit on the same timeline.
- **C++:** `TEMBRA_TRACE_SCOPE("engine.loadClip")` and `TEMBRA_TRACE_COUNTER("engine.cpuLoad", v)` in `engine/include/tembra_trace.h`, expanding to ATrace on Android and the same `os_signpost` shim on iOS, compiled out in release unless `TEMBRA_TRACING=ON`.
- **Rule:** the facade is never called on the audio callback. Both ATrace (a write to `trace_marker`) and `os_signpost` are cheap but not real-time-safe by contract. The audio thread updates atomics; the telemetry drain thread (non-RT) emits counters.
- **Naming:** one catalogue of section names in the spec (`startup.firstFrame`, `timeline.scroll`, `timeline.zoom`, `tuner.frame`, `metronome.tick`, `engine.loadClip`, …), identical on both platforms, so trace-pulse's metric keys (`section.timeline.zoom.sum_ms`) are platform-neutral.

Animation signposts are the exception that earns its place: wrapping a scroll or zoom journey on iOS in an **animation** interval turns a plain duration into hitch count/time/ratio and frame rate for free. The facade needs one extra entry point (`traceAnimation`) that is a normal section on Android (where `FrameTimingMetric` covers frames) and an animation signpost on iOS.

### 6.2 Pipeline level: trace-pulse as a module of this repository

The module is Python plus two native test targets; it is not a Gradle module itself. `tracepulse init` (the scaffolder for foreign projects) can be dropped; Tembra is the only host. The `regressions/` injection catalogue stays as the pipeline's own self-test.

**The `ios` collector** (new `collect_ios.py` / `orchestrate_ios.py`): preflight (`xcrun devicectl list devices` and `devicectl device info lockState`; battery and thermal state are not exposed by `devicectl` on this Xcode, so the test target asserts them itself at start: `UIDevice.current.batteryLevel` with battery monitoring enabled, `ProcessInfo.processInfo.thermalState == .nominal`), build-for-testing once, fresh install (`devicectl device install app`), one unmeasured warm-up launch, `xcodebuild test-without-building -destination 'platform=iOS,id=<udid>' -resultBundlePath …`, then `xcresulttool get test-results metrics` → rows in `samples`/`aggregates` with the same `(round_id, benchmark, metric, iteration, value)` shape; `.xcresult` kept under `data/rounds/<id>/` as the raw artifact; optional `xctrace` capture per round for the audio series (§7). App size from the thinning size report. Both platforms' rounds are separate series in the same database, as the Pixel 6 Pro and 7 Pro already are (`compare` renders them side by side).

### 6.4 Device protocol on iOS

trace-pulse's `doctor` checks have iOS counterparts, with less control than on Android: airplane mode and brightness must be set by hand once (no CLI); thermal state and battery level are readable only in-process (`ProcessInfo.thermalState`, `UIDevice.batteryLevel`; assert `.nominal` and ≥ 50 % at test start, badge the round otherwise; `devicectl device info` exposes neither, verified on Xcode 26.6); the ProMotion refresh rate cannot be pinned from the host, so keep the iPhone 14 (60 Hz) as the series device and never mix with a ProMotion device in one series; fresh install plus warm-up launch is the same recipe. Pairing, Trust and Developer Mode are one-time interactive steps on the phone; wireless pairing needs iOS 27+.

### 6.5 Gate and trend

- **Trend** stays as designed (step fit, confirmation, ratchet, environment guard, report). Precedent: Flutter's DeviceLab feeds Android and iOS series into the same Skia Perf step-fit instance.
- **Coarse gate, implemented once in trace-pulse:** after a round, compare the round median of each gated metric with the median of the last *k* clean rounds of the same series; exceed a per-metric tripwire (first draft 30 %, `gate:` section in `tracepulse.yml`) → non-zero exit → the workflow fails. Platform-neutral, versioned with the config, no GUI involved.
- **Xcode `.xcbaselines`** can stay optional for developers running the perf tests from Xcode on their own Mac+phone pair. They are keyed to that pair, set only in the GUI, and use Apple's stddev rule, so they are not the CI gate.

## 7. Audio-thread health

- **Counters the engine owns** (atomics updated on the callback, read by the drain thread): callback duration last/max/p99-ish histogram (reading the monotonic clock is RT-safe on both platforms), over-budget callback count (duration > buffer period), xruns (Oboe `AudioStream::getXRunCount()` from the drain thread, never from the callback; iOS has no public overload counter, so over-budget count is the proxy), real-time status (Oboe `PerformanceMode::LowLatency` granted; on iOS the `os_workgroup_join` result for any worker thread and the `THREAD_TIME_CONSTRAINT_POLICY` state, since `os_workgroup_join` returns `EINVAL` on a thread without the time-constraint policy, a JUCE-forum finding, not Apple documentation). These are telemetry fields in `AudioEngine`, shown in a debug "Engine stats" panel and used by the pipeline.
- **Lab series.** Android: the drain thread emits them as ATrace counters (`ATrace_setCounter` / `Trace.setCounter`) during the benchmark; trace-pulse's `traces.py` reads the counter track from the Perfetto trace → `audio.callback_max_us`, `audio.over_budget`, `audio.xruns`. Perfetto's `sched` data also shows whether the audio thread was preempted and by whom. iOS: the test journey ends by reading the stats through a debug accessibility element or a JSON file in the app container (`xcrun devicectl device copy from --domain-type appDataContainer --domain-identifier <bundle-id>`, present in this Xcode); plus, per round, an `xctrace record --template 'Audio System Trace' --attach <app>` capture while the journey runs, exported with `--xpath` once the table names are known (spike). Apple's workgroup documentation and WWDC20 10224 are the authoritative description of overloads.
- **Journey:** one "stress" journey on both platforms (playback + metronome + tuner together once the spine exists) drives the `audio.*` series; it is the one family where the two platforms are comparable.
- **Kotlin/Native GC** does not touch the audio thread (C++ only), but its pauses hit UI frames; the safepoint signposts (§5.4) show whether a hitch coincides with a GC pause.
- OboeTester's automated latency/glitch tests (intent-driven, loopback adapter) give a device-level audio baseline independent of the app; optional.

## 8. Field data

- **iOS MetricKit:** an `MXMetricManagerSubscriber` (iOS 27 adds `MetricManager` with async delivery; `MXMetricPayload` is deprecated in 27.2 in favour of `MetricReport`) delivers daily metric payloads (launch, hang time, hitch time ratio, CPU, peak memory, GPU, disk writes, custom `mxSignpost` intervals) and immediate diagnostics (hangs, CPU exceptions, disk-write exceptions, crashes). Minimal implementation: subscribe in `iOSApp.swift`, write `jsonRepresentation()` to the app's Documents directory, add an export action in a debug screen. No backend needed for an open-source app.
- **Android:** Vitals in the Play Console once published (no code); JankStats optional for per-frame field data with UI-state annotation.
- **DAW-specific gap:** none of these see the audio callback. The engine's counters (§7) should be logged per session into a local "session health" file that a user can attach to a bug report; that is the field signal for glitches.

## 9. CI: two workflows

### 9.1 `perf-devices.yml`: self-hosted runner, second Mac, devices on USB (primary series)

GitHub Actions self-hosted runner installed as a service (`./svc.sh install && ./svc.sh start`) on the second Mac, labelled e.g. `self-hosted, macOS, tembra-devices`. Triggered on a schedule and on demand (`workflow_dispatch`), never per push: a round is 15 minutes per device, and the detector wants evenly spaced rounds. Steps: checkout, `tracepulse doctor` (both devices), `tracepulse run -c pixel/…` and `tracepulse run -c iphone14/…` (sequentially; the Mac is the bottleneck, not the phones), `tracepulse analyze`, `tracepulse report`, coarse gate (§6.5), upload `report.html` and the round's raw artifacts as workflow artifacts, optionally publish the report. Requirements: the Mac stays logged in and awake (`caffeinate -s`; your notes from the trace-pulse chains apply), the iPhone paired and in Developer Mode, the runner user able to reach the SQLite history (keep `data/` on that Mac, not in git, as trace-pulse already does).

Maestro has no role in measuring here (§9.3); the journeys are UiAutomator inside Macrobenchmark and XCUITest inside `measure`, as Google and Apple intend.

**Runner hardware constraint (checked 2026-10-06).** The second Mac available is a 2015 MacBook Pro. Apple's compatibility table caps it at macOS Monterey 12 (Ventura starts at 2017 models), and Monterey caps Xcode at 14.x, whose device support ends at iOS 16.4; Xcode 26.x needs macOS 15.6/26.2 and is what the iPhone 14 on a current iOS requires. So the 2015 machine can be the **Android** runner (JDK 21, platform-tools, Python and the GitHub runner all run on Monterey x64) but not the iOS runner without an unsupported OpenCore Legacy Patcher install, which is the wrong foundation for a machine whose job is to be boring. The iPhone series therefore runs from the Apple Silicon Mac (on demand, or that Mac registered as a second self-hosted runner with a schedule), or from a later Apple Silicon Mac mini if a dedicated iOS runner is wanted.

**Remote iPhone: use Apple's network-device support, not usbmuxd forwarding (checked 2026-10-08).** Forwarding `/var/run/usbmuxd` over TCP (`socat`, Corellium's `usbfluxd`) only carries legacy lockdown services. Since iOS 17, developer services (Instruments/DVT, debugserver, core device operations) go over the CoreDevice RSD/RemoteXPC tunnel, which over USB rides the device's NCM network interface, not the usbmuxd socket (pymobiledevice3 iOS 17 tunnels guide). The owner's iPhone 14 (iOS 27.0.1) shows `tunnelState: connected`, `tunnelTransport: tcp`, `*.coredevice.local` in `devicectl device info details`; the 2015 Mac on Monterey has no CoreDevice stack to forward. The supported path is Apple's: "You can disconnect the physical cable and run apps on the device through Xcode using Wi-Fi with IPv6 enabled on the same network as your Mac" (Device Hub doc; wireless pairing needs iOS 27+, cable otherwise). So the iPhone can sit beside the Android devices, powered by the 2015 Mac's USB port, while the Apple Silicon Mac runs `xcodebuild test`, `devicectl` and `xctrace` against it over Wi-Fi. To test in the spike: install speed, reconnect behaviour, IPv6 on the LAN, and Wi-Fi re-enabled under airplane mode for the device protocol.

### 9.2 `perf-farm.yml`: a fixed, small set of happy-path runs on a cloud farm

**Firebase Test Lab status (checked 2026-10-06):** "deprecated and will be fully shut down on September 30, 2027"; successor Google Cloud Developer Device Platform (`gcloud beta device-run sessions submit instrumentation|xctest`, Preview) matches FTL rates through 2027-04-30 and **requires billing enabled**. Today's Spark quota is 10 virtual + 5 physical test runs per day at no cost (the "15" you remembered); Blaze is $5 per physical device-hour and $1 per virtual device-hour with 30 physical and 60 virtual minutes per day free, billed per minute.

What survives the round trip: **Android** returns `benchmarkData.json` and the `.perfetto-trace` files with `--directories-to-pull /sdcard/Download` and `--environment-variables additionalTestOutputDir=/sdcard/Download,no-isolated-storage=true` (Google's own Macrobenchmark-on-FTL sample). **iOS** takes a zipped `.xctestrun` build (`gcloud firebase test ios run --test MyTests.zip --device model=…,version=…`), has no `--directories-to-pull`, and the docs do not say whether the `.xcresult` bundle lands in the results bucket; one practitioner (2024) parsed `xcodebuild_output.log` with regular expressions instead. No `xctrace` is possible on FTL (no host shell). AWS Device Farm is the fallback that documents artifact return: it runs your own `xcodebuild` on a managed macOS host and returns anything placed in `$DEVICEFARM_LOG_DIR`, so an `.xcresult` survives. BrowserStack returns result bundles and sells CPU/memory/FPS profiling on its Pro plans. Marathon fans out iOS tests to Macs over SSH but has no physical-iOS device type. DeviceFarmer/STF is Android-only.

What a fixed daily set costs on DDP: one Android and one iOS smoke run of about ten device-minutes each (install, warm-up, startup × 5, one journey × 5) is 20 physical device-minutes per day, so roughly **$50 per month at preview rates and $120 per month from April 2027**; three runs a week instead of daily is about $22 and $52. Emulator runs are a tenth of that but are not performance evidence.

So: **there is no sustained zero-cost farm for both platforms after Firebase Test Lab ends.** Until then, Spark's five physical runs per day cover a daily Android plus iOS smoke pair at no cost and with no billing account. After that the choices are a modest DDP or AWS budget, one-time credits as a bridge, or dropping the farm and keeping only the self-hosted second Mac, which is the free real-device path for as long as you own the phones.

Plan: write the farm step as a thin adapter in trace-pulse (`farm: ftl | ddp | aws`) that submits, waits, downloads, and hands the artifacts to the same collectors. Start on FTL Spark (one Android physical run and one iOS physical run per day fit in 5), spike the iOS artifact question first (§10), and decide before 2027-04-30 between a DDP budget (billing enabled), AWS Device Farm, or no farm at all. Farm rounds are a **separate series** per farm device model, badged as farm rounds; they never mix with the protocol-controlled USB series. Their value is device breadth and a run when no device is attached, not low noise: farms give no airplane mode, no refresh-rate pin, no thermal gate.

### 9.3 Maestro's role

Per its documentation: iOS flows run on simulators only, locally and in Maestro Cloud ($250 per device-month, simulators and emulators); Android flows run on USB-connected physical devices; `maestro record` records video; there is no performance-measurement feature.

Physical iPhones, checked on 2026-10-06 against the repository rather than the docs: the README on `main` says "Physical iOS devices are not yet supported"; the latest release is `cli-2.11.0` (2026-09-29); PR #3609 (merged 2026-09-18 by a maintainer) deliberately removed connected iPhones from device selection and hid `--apple-team-id`, because flows "hit an unimplemented method in the devicectl driver" after a multi-minute `xcodebuild`; the two community implementations (PR #2856, 2025-11; PR #3100, 2026-03) were closed unmerged, and the maintainer's position on the tracking issue (#686, open since 2023-01) is "staff intend to work on it soon… only partial implementations". The mechanism those PRs used is instructive: Maestro's iOS driver is an XCTest runner (`maestro-driver-ios`) that must be code-signed with your Apple team ID and built with `xcodebuild build-for-testing -destination 'platform=iOS,id=<udid>'`, launched with `devicectl`, and reached over USB through `iproxy` from libimobiledevice. Maestro dropped `idb` for simulators in 2023 in favour of that driver, and `applesimutils` is a simulator-only permissions tool, so neither is a route to a real iPhone. Running a patched Maestro from PR #3100 is technically possible and explicitly unsupported. Maestro drives through the accessibility layer and never owns the process, so a flow can run while `record_android_trace`/`perfetto` or (on a simulator) `xctrace --attach` records; nothing documents this, nothing forbids it. Where that fits here: cross-platform smoke journeys on the hosted-CI lane (Android emulator, iOS simulator) with the same YAML on both, and Android USB smoke flows on the second Mac. For the iPhone, the drivers are `xcodebuild`/`devicectl`/XCUITest, exactly as JetBrains' own harness does it.

## 10. Risks, mismatches and spikes

Each spike is half a day or less and should precede the plan.

1. **iOS per-iteration JSON on a real run.** Write one `measure(metrics: [XCTClockMetric(), XCTMemoryMetric()], options: 20 iterations)` test in a throwaway target, run it on the iPhone 14, inspect `xcresulttool get test-results metrics` output and confirm the default `iterationCount` while at it.
2. **FTL iOS artifacts.** One Spark run of that target; list the results bucket; decide FTL vs AWS for the iOS farm half.
3. **Audio System Trace schema.** `xctrace record --template 'Audio System Trace' --device <udid> --attach <app> --time-limit 20s`, then `xctrace export --toc`; record the table names for `traces_ios.py`.
4. **Unattended `xctrace`/`xcodebuild` on a locked, logged-in Mac.** Lock the second Mac, trigger a run over SSH; this decides whether the runner needs the screen awake.
5. **`Modifier.testTag` → `accessibilityIdentifier` on iOS** in CMP 1.12.1, so XCUITest can find the same elements UiAutomator finds via `testTagsAsResourceId`.
6. **iOS app size:** confirm the app-thinning size report from `xcodebuild -exportArchive` (export options `thinning`) is scriptable and which bytes to store.
7. **Animation signposts under Compose:** confirm an animation `os_signpost` opened in Kotlin (through the shim) around a scroll journey yields hitch and frame-rate columns in `XCTOSSignpostMetric` on the device.
8. **`frames` family parity.** If the hitch ratio proves too blunt for the timeline work, add the in-app CADisplayLink statistics path; decide after the first ten iOS rounds.
9. **Kotlin/Native allocations in Instruments** (mmap allocator): check once whether `disableMmap=true` is needed in perf builds to see Kotlin allocations in Allocations; otherwise rely on VM Tracker.
10. **Perfetto `cpu_profile` on the Pixels:** confirm the Android 15+ note and the `profileable` manifest flag on the release build type used for rounds.

Known mismatches to accept, not solve: TTFD semantics differ per platform; frames are percentiles on Android and hitch ratios on iOS; memory quantities differ; baselines in Xcode are per Mac+device. All are handled by keeping per-platform series and per-series gates.

## 12. Decisions taken by the owner during this research (2026-10-06)

- Scope: all four kinds (regression tracking across builds, deep-dive interactive profiling, audio-thread health, field data), with each tool classified by where it runs (§3).
