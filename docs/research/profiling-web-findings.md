# Web research findings: iOS counterpart to trace-pulse, cross-platform tracing, device farms

Compiled 2026-10-06. Local toolchain used as a primary source where noted: Xcode 26.6 (17F113), `xcresulttool version 24757, schema 0.1.0 (legacy format 3.58)`, `android` CLI 1.0.16500706.

"Where it runs" tags, applied to every tool below:

- `[usb]` real device attached to the owner's Mac (local/USB or Wi‑Fi pairing)
- `[farm]` real device on a hosted farm (FTL/DDP, AWS, BrowserStack, Sauce…)
- `[sim-ci]` simulator/emulator on hosted CI (GitHub-hosted macOS, Xcode Cloud, Maestro Cloud)
- `[field]` production/TestFlight telemetry
- `[dev]` developer-interactive GUI only (Xcode, Instruments, Android Studio)

## A. iOS standard profiling that can run from the command line / CI

### A1. XCTest performance tests, metrics, baselines — `[usb]` `[farm]` `[sim-ci]` `[dev]`

- API: `func measure(metrics: [any XCTMetric], options: XCTMeasureOptions, block: () -> Void)`; iOS 13.0+, macOS 13.0+(Catalyst 13.0+), tvOS 13.0+, watchOS 7.0+, visionOS 1.0+. Siblings: `measure(_:)`, `measure(metrics:block:)`, `measure(options:block:)`, `measureMetrics(_:automaticallyStartMeasuring:for:)` (https://developer.apple.com/documentation/xctest/xctestcase/measure(metrics:options:block:)).
- `XCTMetric` conformers (current docs): `XCTApplicationLaunchMetric`, `XCTCPUMetric`, `XCTClockMetric`, `XCTHitchMetric`, `XCTMemoryMetric`, `XCTOSSignpostMetric`, `XCTStorageMetric`. Protocol requires `willBeginMeasuring()`, `didStopMeasuring()`, `reportMeasurements(from:to:) -> [XCTPerformanceMeasurement]` (https://developer.apple.com/documentation/xctest/xctmetric).
- `XCTHitchMetric` is new: `class XCTHitchMetric`, `init(application: XCUIApplication)`, available iOS/iPadOS/macOS/tvOS/watchOS **26.0+**; "A metric to measure the number of hitches your UI encounters in a performance test." Requires a UI test (takes an `XCUIApplication`) (https://developer.apple.com/documentation/xctest/xcthitchmetric).
- `XCTOSSignpostMetric`: "captures the time that elapses between the begin and end events for a specific named os_signpost region. It doesn't record any results when there isn't a matching pair of begin and end events." `init(subsystem:category:name:)`; built-ins `navigationTransitionMetric`, `customNavigationTransitionMetric`, `scrollingAndDecelerationMetric`; deprecated `applicationLaunch`, `scrollDecelerationMetric`, `scrollDraggingMetric` (https://developer.apple.com/documentation/xctest/xctossignpostmetric).
- `XCTMeasureOptions`: `iterationCount: Int`, `invocationOptions: XCTMeasureOptions.InvocationOptions` (manual start/stop), `class var default`. "A performance test runs its block `iterationCount+1` times, ignoring the first iteration and recording metrics for the remaining iterations. The test ignores the first iteration to reduce measurement variance associated with 'warming up' caches and other first-run behavior." The default value of `iterationCount` is not stated on the page (UNVERIFIED; commonly observed as 5) (https://developer.apple.com/documentation/xctest/xctmeasureoptions/iterationcount).
- Apple's guidance ("Writing and running performance tests"): default `measure(_:)` records "the time spent in the measured code, in seconds"; baseline is set interactively ("click the icon next to the performance measurement function call… Click Set Baseline"; Edit → "Enter a value in the Max STDDEV field"). Pass/fail rule: "The test fails if the recorded metric is worse than the baseline value by more than the maximum standard deviation." CI-variance guidance: "Configure your scheme to build for testing using the Release build configuration, and turn off the 'Debug executable' setting." and "Configure your test plan to disable code coverage and the runtime sanitization options." The page says nothing about CI, Xcode Cloud, or setting baselines non-interactively (https://developer.apple.com/documentation/xcode/writing-and-running-performance-tests).
- Apple's umbrella page: "Profile on actual devices instead of simulators for higher-fidelity measurements" (https://developer.apple.com/documentation/xcode/improving-your-app-s-performance).
- Baseline files on disk (Apple does not document the format; verified against a public repo): `<Project>.xcodeproj/xcshareddata/xcbaselines/<TargetUUID>.xcbaseline/Info.plist` holds `runDestinationsByUUID` → `{ localComputer { modelCode, cpuKind, cpuCount, cpuSpeedInMHz, platformIdentifier … }, targetArchitecture, targetDevice { modelCode e.g. iPhone12,1, platformIdentifier e.g. com.apple.platform.iphonesimulator } }`; a sibling `<RunDestinationUUID>.plist` holds `classNames → <TestClass> → <testName()> → <metric id, e.g. com.apple.XCTPerformanceMetric_WallClockTime> → { baselineAverage: 0.189, baselineIntegrationDisplayName: "Local Baseline" }` (https://github.com/Boris-Em/ColorKit/tree/master/ColorKit/ColorKit.xcodeproj/xcshareddata/xcbaselines/A181C8602404728F0008D4B7.xcbaseline). So baselines are keyed by host Mac model **and** target device/platform; a baseline recorded on one Mac+device pair is not consulted for another. The per-metric threshold keys exposed in results are `maxPercentRegression`, `maxPercentRelativeStandardDeviation`, `maxRegression`, `maxStandardDeviation` (see A2). Setting baselines on CI therefore means committing plist files whose `runDestinationsByUUID` matches the CI Mac + device — feasible but undocumented by Apple (UNVERIFIED as a supported workflow).
- `xcodebuild` flags (local `xcodebuild -help`, Xcode 26.6): `-enablePerformanceTestsDiagnostics YES|NO` "enables performance trace and memgraph collection for performance XCTests"; `-resultBundlePath PATH`; `-test-iterations <n>`, `-retry-tests-on-failure`, `-run-tests-until-failure`, `-test-repetition-relaunch-enabled YES|NO`; `-testPlan`, `-only-testing:ID`, `-collect-test-diagnostics on-failure|never`.

### A2. Reading performance results out of `.xcresult` — `[usb]` `[farm]` `[sim-ci]`

- Xcode 16 deprecated `xcresulttool get object` (requires `--legacy`; error text "This command is deprecated and will be removed in a future release, --legacy flag is required to use it") and added `get test-results {summary|tests|insights|test-details|activities|metrics}`, `get build-results`, `export {diagnostics|attachments|metrics}`, `metadata get`, `merge`; flags `--path`, `--test-id`, `--format json|raw|text|markdown`, `--compact`, `--output-path` (man page, dated 2024: https://keith.github.io/xcode-man-pages/xcresulttool.1.html; deprecation thread: https://github.com/fastlane/fastlane/issues/22132; Apple forum: https://developer.apple.com/forums/thread/763050).
- Verified locally (Xcode 26.6): `xcrun xcresulttool get test-results metrics --path X.xcresult [--test-id <id>] [--compact]` — "Get performance metrics… All the available metrics will be included if no test identifier is provided." Its JSON schema (`--schema`, version 0.1.0): `TestWithMetrics { testIdentifier, testIdentifierURL, testRuns[] }`, `TestRunWithMetrics { testPlanConfiguration {configurationId, configurationName}, device {deviceId, deviceName}, metrics[] }`, `Metric { displayName, unitOfMeasurement, measurements: [double] (per-iteration), identifier, baselineName, baselineAverage, maxRegression, maxPercentRegression, maxStandardDeviation, maxPercentRelativeStandardDeviation, polarity }`. `xcrun xcresulttool export metrics --path X.xcresult --output-path DIR [--test-id …]` writes "CSV files with performance measurements" plus a `manifest.json`. Per-iteration values are therefore first-class in the new API — no legacy parsing needed.
- Legacy (`--legacy`) object graph type `ActionTestPerformanceMetricSummary` has the same fields (`displayName, unitOfMeasurement, measurements:[Double], identifier, baselineName, baselineAverage, maxPercentRegression, maxPercentRelativeStandardDeviation, maxRegression, maxStandardDeviation`) (format 3.19 dump: https://gist.github.com/barakwei/e359b164813e042f672930e56eafe8b2).
- Open-source parsers: `a7ex/xcresultparser` (JUnit/Cobertura/Sonar/HTML/MD from xcresult; no performance-metric extraction documented; https://github.com/a7ex/xcresultparser); `ChargePoint/xcparse` (screenshots/logs; https://github.com/ChargePoint/xcparse); fastlane `trainer` (JUnit only); Chromium's iOS bot parser switches on Xcode 16 to `xcresulttool get test-results summary|tests --format json` and `export diagnostics|attachments`, and only appends `--legacy` for old calls — it does not read perf metrics (https://chromium.googlesource.com/chromium/src/+/HEAD/ios/build/bots/scripts/xcode_log_parser.py). `SoaurabhK/XCTool` parses performance summaries from xcresult via `xcresulttool` (https://github.com/SoaurabhK/XCTool). Flutter tracked the same deprecation (https://github.com/flutter/flutter/issues/151502).

### A3. `xctrace` — `[usb]` `[dev]` (not `[farm]`, not `[sim-ci]` for devices)

- Man page (dated January 3, 2023; https://keith.github.io/xcode-man-pages/xctrace.1.html): `xctrace record` options `--output`, `--template`, `--device`, `--launch`, `--attach`, `--all-processes`, `--time-limit`, `--target-stdout`, `--target-stdin`, `--env`, `--package`, `--append-run`, `--run-name`, `--no-prompt`, `--notify-tracing-started`. Verbatim: `--device` "Record on a device with the given name or UDID. If not specified, then local device is chosen for the recording."; `--launch` "Launch and record process with the given name or path and provided arguments list."; `--attach` "Attach and record running process with the given name or pid."; `--time-limit` "Limits the recording to the specified time period. Example: '--time-limit 5s' or '--time-limit 1m'"; `--instrument` "Adds Instrument with the specified name to the recording configuration."; `--no-prompt` "Skip any prompts that would be otherwise presented (like privacy warnings)".
- `xctrace export --input X.trace --toc` and `--xpath '/trace-toc/run[@number="1"]/data/table[@schema="my-table-schema"]'` export XML; `--xpath '/trace-toc/run[@number="1"]/processes'` lists binaries with UUID/load address; `xctrace symbolicate --input X.trace --dsym Lib.dSYM`; `xctrace list devices|templates|instruments|runs`. Examples from the man page: `xctrace record --all-processes --template 'Time Profiler' --time-limit 5s`; `xctrace record --template 'Time Profiler' --device-name "Chad's iPhone" --attach 'Trailblazer'`; `xctrace record --template 'Time Profiler' --target-stdout - --launch -- /tmp/tool arg1 arg2`.
- Templates on Xcode 26.6 (local `xcrun xctrace list templates`): Activity Monitor, Allocations, **Animation Hitches**, App Launch, **Audio System Trace**, CPU Counters, CPU Profiler, Core ML, Data Persistence, File Activity, Game Memory, Game Performance, Game Performance Overview, Leaks, Logging, Metal System Trace, Network, Power Profiler, Processor Trace, RealityKit Trace, Swift Concurrency, SwiftUI, System Trace, Tailspin, Time Profiler. Instruments include **Audio Client, Audio Server, Audio Statistics**, Core Animation FPS, Core Animation Commits, Display, Frame Lifetimes, Hangs, **Hitches**, **Points of Interest**, os_signpost, os_log, Thread State Trace, Time Profiler, VM Tracker. Apple publishes no web doc for the Audio System Trace template; the only primary source is the Instruments app itself.
- Unattended use on a USB iPhone: the man page documents `--device` + `--launch`/`--attach` and `--no-prompt`, and JetBrains' own iOS benchmark harness enumerates devices with `xcrun xctrace list devices` (see B9). Neither the man page nor Apple's Developer Mode page states whether the device must be unlocked; Apple's Developer Mode doc only says it gates "building and running an app from Xcode, or installing an .ipa file with Apple Configurator" (https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device). Unlock requirement: UNVERIFIED.

### A4. os_signpost / OSSignposter from Swift and C — `[usb]` `[dev]` `[field]`

- Swift: `let signposter = OSSignposter(); let id = signposter.makeSignpostID(); let state = signposter.beginInterval("name", id: id); … signposter.endInterval("name", state)`; "The os_signpost instrument displays separate rows for each subsystem and category combination" (https://developer.apple.com/documentation/os/recording-performance-data).
- C (`<os/signpost.h>`): `#define os_signpost_interval_begin(log, interval_id, name, ...)`, pair with `os_signpost_interval_end`; "Calling this function is equivalent to calling `os_signpost_emit_with_type` with a type of `OS_SIGNPOST_INTERVAL_BEGIN`" (https://developer.apple.com/documentation/os/os_signpost_interval_begin). Animation variant `#define os_signpost_animation_interval_begin(log, interval_id, name, ...)` (https://developer.apple.com/documentation/os/os_signpost_animation_interval_begin). Swift: `os_signpost(.animationBegin, log:, name:)` (WWDC20 10077, below).
- How XCTOSSignpostMetric measures them: for a plain interval it reports duration; for an **animation** interval (WWDC20 10077, "Eliminate animation hitches with XCTest"): "when using an animation os_signpost interval, you will receive not just duration, but also three hitch related metrics, frame rate, and frame count" — hitch count, hitch time, hitch time ratio, frame rate, frame count; thresholds "less than five milliseconds per second is good… five-to-ten… should be investigated… ten milliseconds per second or more… immediate action" (https://developer.apple.com/videos/play/wwdc2020/10077/).
- Points of Interest: category `OS_LOG_CATEGORY_POINTS_OF_INTEREST` is rendered by the "Points of Interest" instrument (listed locally; Apple's os docs reference the constant — exact page not fetched, UNVERIFIED URL).

### A5. MetricKit — `[field]` only

- "The system delivers metric reports about the previous 24 hours to your app at most once per day. Diagnostic reports arrive immediately in iOS 15 and later, and macOS 12 and later." Platforms iOS 13+, macOS 12+, visionOS 1+ (no perf metrics on visionOS). iOS 27 adds `MetricManager` with async-sequence delivery and new `MetricReport`/`DiagnosticReport`/`MetricResult` types (https://developer.apple.com/documentation/metrickit).
- Legacy payloads are deprecated: `MXMetricPayload` "Deprecated in iOS 27.2… Use MetricReport instead"; properties include `animationMetrics` (`MXAnimationMetric.scrollHitchTimeRatio`, deprecated 27.2, "Use MetricResult, and read the HitchTimeMetric case instead"), `applicationLaunchMetrics`, `applicationResponsivenessMetrics`, `signpostMetrics: [MXSignpostMetric]`, `cpuMetrics`, `memoryMetrics`, `gpuMetrics`, `displayMetrics`, `applicationExitMetrics`, `jsonRepresentation()` (https://developer.apple.com/documentation/metrickit/mxmetricpayload, https://developer.apple.com/documentation/metrickit/mxanimationmetric). Whether payloads are delivered to development builds is not stated on these pages (UNVERIFIED; the daily cadence alone makes it unsuitable for CI).

### A6. Hitches: Apple guidance and what XCTest has — `[usb]` `[dev]`

- Definitions: "The difference between the actual frame lifetime and the expected frame lifetime is called the hitch duration"; commit hitch vs render hitch; Organizer "Hitches metric measures hitch rate in milliseconds of pause per second (ms/s)… at or below 10 ms/s is good; at or below 25 ms/s is a warning; at or below 50 ms/s is critical; and above 50 ms/s warrants immediate attention"; "The Hitches instrument isn't available for visionOS" (https://developer.apple.com/documentation/xcode/understanding-hitches-in-your-app). Note the two different scales: WWDC20's XCTest thresholds (5/10 ms/s) vs the Organizer field metric (10/25/50 ms/s).
- XCTest hitch measurement today: (a) `XCTOSSignpostMetric` over an animation signpost (Xcode 12+, WWDC20 10077); (b) `XCTHitchMetric(application:)` on OS 26+ (A1). The Instruments template is "Animation Hitches" and the instrument is "Hitches" (local `xctrace list`).

### A7. Real iPhones from CI

- Xcode Cloud — `[sim-ci]`: test action runs `xcodebuild build-for-testing` then `test-without-building`; "Available destinations depend on the workflow's environment setting" (https://developer.apple.com/documentation/xcode/configuring-your-xcode-cloud-workflow-s-actions). WWDC22 110361: "Tests run in Xcode Cloud make use of a fresh simulator" (https://developer.apple.com/videos/play/wwdc2022/110361/). No Apple page offers physical-device destinations (absence verified on the above pages; a formal "not supported" statement was not found).
- GitHub-hosted macOS runners — `[sim-ci]`: VMs; no physical iOS devices can be attached (inference from the hosted-runner model; GitHub's docs do not discuss iOS devices).
- Self-hosted Mac + USB iPhone — `[usb]`: `xcodebuild test -destination 'platform=iOS,id=<udid>'`; `xcrun devicectl device install app --device <udid> App.app`, `xcrun devicectl device process launch --console --device <udid> <bundle-id> -- <args>` (local `devicectl --help`: "Automation and integration with other tools is supported via JSON output captured to a file, which is versioned and will remain stable"; `--console` "Attaches the application to the console and waits for it to exit"; env via `DEVICECTL_CHILD_` prefix or `--environment-variables '{"K":"V"}'`; `--terminate-existing`, `--start-stopped`). Pairing: `xcrun devicectl manage pair --device <udid>`; Device Hub: "When the Trust This Computer dialog appears on the device, tap Trust"; "If necessary, enable Developer Mode on the device"; wireless: "Upgrade your iPhone or iPad to iOS or iPadOS 27 or later to wirelessly pair it; otherwise, use a cable", same Wi‑Fi, IPv6 for tvOS/visionOS (https://developer.apple.com/documentation/xcode/managing-your-simulated-and-physical-devices-in-device-hub). Developer Mode: "In the Privacy & Security settings on the device, turn on the Developer Mode switch under Security", device restarts, passcode confirm; "After you turn off Developer Mode, you can't run apps from Xcode on the device until you turn on Developer Mode again" (https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device). Trust + Developer Mode are one-time interactive steps on the phone.
- GitHub Actions self-hosted runner as a macOS service: `./svc.sh install` / `./svc.sh start`; the page gives no guidance on logged-in sessions or auto-login (https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/configuring-the-self-hosted-runner-application-as-a-service).

## B. Kotlin/Native and Compose Multiplatform on iOS

### B8. Kotlin/Native in Instruments — `[usb]` `[dev]`

- GC monitoring (page dated 29 May 2026): `-Xruntime-logs=gc=info` ("Currently, the logs are only printed to stderr"); `kotlin.native.binary.enableSafepointSignposts=true` then in Instruments pick the `os_signpost` template, subsystem `org.kotlinlang.native.runtime`, category `safepoint` to see GC pauses; `kotlin.native.binary.gc=pmcs|noop`, `kotlin.native.binary.gcMarkSingleThreaded=true`; `kotlin.native.internal.GC.collect()` (https://kotlinlang.org/docs/native-memory-manager.html).
- Binary options (page dated 31 Aug 2026): set via `gradle.properties` `kotlin.native.binary.<name>=…`, `binaryOption("name","value")`, or `-Xbinary=name=value`. `gc` = `cms` (default; "cms is default since 2.4.0"), `pmcs`, `stwms`, `noop`; `enableSafepointSignposts` (false default) "Enables tracking GC-related pauses… for debugging in Xcode Instruments"; `appStateTracking`; `pagedAllocator` (true default; "When false, the memory allocator reserves memory on a per-object basis. Experimental since 2.2.0"); `mmapTag` ("Controls memory tagging, necessary for memory consumption tracking on Apple platforms. Values 240–255 (default 246)… Available since 2.2.0"); `disableMmap` ("When true, uses the malloc memory allocator instead of mmap. Available since 2.2.0"); `sourceInfoType` = `libbacktrace|coresymbolication|noop`; `stackProtector`; `smallBinary`; `enableReleaseBinaryCache` ("Experimental since 2.4.20") (https://kotlinlang.org/docs/native-binary-options.html). Consequence for the Allocations instrument: Kotlin's default allocator is mmap-based and tagged (VM tag 246) — individual Kotlin object allocations are not malloc calls, so they appear as tagged VM regions (VM Tracker) rather than as Allocations-instrument events unless `disableMmap=true`. This inference is from the option descriptions; Apple-side behaviour UNVERIFIED.
- Debug info/symbolication (page dated 23 Jul 2026): "The Kotlin/Native compiler generates .dSYM files for release (optimized) binaries on Apple platforms by default. When building in Xcode, the IDE looks for .dSYM files in standard locations and uses them automatically for symbolication"; DWARF 2; `-Xadd-light-debug=enable` is documented for non-Apple platforms (https://kotlinlang.org/docs/native-debugging.html). `-Xbinary=stripDebugInfoFromNativeLibs=false` (keeps runtime debug info) appears only in community Slack archives — UNVERIFIED in official docs.
- Recent releases: 2.2.20 added stack canaries, `smallBinary`, Swift export (experimental), Xcode 26 support in 2.2.21, deprecation of x86_64 Apple targets (https://kotlinlang.org/docs/whatsnew2220.html); 2.3.0 (16 Dec 2025) raised min iOS to 14.0, "release builds can be up to 40% faster", Compose group-key stack traces for R8-minified apps (https://kotlinlang.org/docs/whatsnew23.html).
- os_signpost from Kotlin: the iOS platform lib `platform.darwin` bundles `os/log.h os/signpost.h` (https://github.com/JetBrains/kotlin/blob/master/kotlin-native/platformLibs/src/platform/ios/darwin.def); `os_signpost_interval_begin` is a variadic C macro, so a tiny C/ObjC shim is the practical route — exactly what Compose does (B10).

### B9. Compose Multiplatform iOS rendering and JetBrains benchmarks — `[usb]` `[dev]`

- Frame production (source, `jb-main`): `MetalRedrawer.ios.kt` renders Skia pictures into a `CAMetalLayer` drawable (`Surface.makeFromBackendRenderTarget`, `flushAndSubmit`, `presentDrawable`), with `trace("MetalRedrawer:draw")`, `…:pictureRecording`, `…:nextDrawable`, `…:encodeAndPresent`, `…:waitTransaction` sections; `DisplayLinkListener.ios.kt` uses `CADisplayLink` on `NSRunLoop.mainRunLoop` (https://github.com/JetBrains/compose-multiplatform-core/blob/jb-main/compose/ui/ui/src/iosMain/kotlin/androidx/compose/ui/window/MetalRedrawer.ios.kt, …/DisplayLinkListener.ios.kt). `ComposeContainerConfiguration`: `parallelRendering: Boolean = true` ("encode the rendering commands on a dedicated render thread, when possible"), `opaque: Boolean = true` ("disabling opaque layer may affect performance") (https://github.com/JetBrains/compose-multiplatform-core/blob/jb-main/compose/ui/ui/src/iosMain/kotlin/androidx/compose/ui/uikit/ComposeContainerConfiguration.ios.kt). Docs (1.8.0, page dated 20 Feb 2026): "Compose Multiplatform for iOS now supports offloading rendering tasks to a dedicated render thread"; "The `enableTraceOSLog()` function no longer requires experimental opt-in… trace information that can be analyzed using Xcode Instruments" (https://kotlinlang.org/docs/multiplatform/whats-new-compose-180.html). JetBrains' 1.8.0 claims ("Startup time is comparable to native apps", "Scrolling performance is on par with SwiftUI, even on high-refresh-rate devices") point to the benchmark repo (https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/).
- `benchmarks/multiplatform` (https://github.com/JetBrains/compose-multiplatform/tree/master/benchmarks/multiplatform): modes `SIMPLE`, `VSYNC_EMULATION`, `REAL` ("requires a device with a real display"), `STARTUP` (`timeToMain`, `timeFromMainToFirstFrame`, `timeOfFirstFrame`, `timeToNthFrame`, `longestFrames`); arguments `modes`, `benchmarks`, `warmupCount`, `frameCount`, `parallel` (iOS only), `saveStatsToCSV`, `saveStatsToJSON`, `versionInfo`; scripts `run_benchmarks.main.kts <platform> runs=N`, `compare_benchmarks.main.kts v1= v2=`, `find_degradation.main.kts` (">5% increase in time" binary search). iOS path: `xcrun xctrace list devices` → `./run_ios_benchmarks.main.kts <UDID>`; the script runs `xcodebuild build -project iosApp.xcodeproj -scheme iosApp -configuration Release -destination id=<udid>`, `xcrun devicectl device install app --device <udid> <app>`, `xcrun devicectl device process launch --console --device <udid> <bundleId> --`, and reads benchmark JSON from the app's stdout (`printJsonToOutput = true` in `main.ios.kt`); results in `benchmarks/build/benchmarks/text-reports/`. The in-app measurement uses `UIScreen.mainScreen.maximumFramesPerSecond` and Kotlin `TimeSource.Monotonic` — i.e. **self-instrumentation printed to the console**, not Instruments. No `-Dcompose.benchmark…` JVM flags exist on iOS; configuration is by launch arguments.
- Compose compiler metrics/reports for KMP: `composeCompiler { metricsDestination, reportsDestination, stabilityConfigurationFiles }`; "To distinguish metrics files for different KotlinTargets, the plugin uses a… subdirectory structure based on KotlinTarget.disambiguationClassifier/KotlinCompilation.compilationName", e.g. `<metricsDestination>/jvm/main`; `includeTraceMarkers` defaults to `true` ("inject additional tracing information… composable functions in the Android Studio system trace profiler"); `targetKotlinPlatforms` default "all Kotlin platforms" (https://github.com/JetBrains/kotlin/blob/master/libraries/tools/kotlin-compose-compiler/src/common/kotlin/org/jetbrains/kotlin/compose/compiler/gradle/ComposeCompilerGradlePluginExtension.kt). So stability reports work for iOS targets (per-target folders).

- CI (page updated 2026-09-21): "Run benchmarks on physical Android devices. ### C12. Perfetto on Android — `[usb]` `[farm]`

- Track events from C++: `PERFETTO_DEFINE_CATEGORIES(...)`, `PERFETTO_TRACK_EVENT_STATIC_STORAGE()`, `TRACE_EVENT("cat","name")`; backends `perfetto::kInProcessBackend` / `kSystemBackend` (https://perfetto.dev/docs/instrumentation/tracing-sdk, https://perfetto.dev/docs/instrumentation/track-events).
- ATrace NDK: `#include <android/trace.h>`, `ATrace_beginSection("…")`, `ATrace_endSection()`, `ATrace_setCounter(name, value)`; "You cannot choose a tag/category when using the NDK API. Implicitly all calls use the ATRACE_TAG_APP tag" (https://github.com/google/perfetto/blob/main/docs/getting-started/atrace.md; NDK ref https://developer.android.com/ndk/reference/group/tracing).
- Callstack sampling: data source `linux.perf` with `perf_event_config { timebase { counter: SW_CPU_CLOCK frequency: 100 … } callstack_sampling { scope { target_cmdline: "pkg" } kernel_frames: true } }`; "the app has to be declared as either profileable or debuggable in the manifest (or you must be on a debuggable build of the android OS)"; helper `python3 cpu_profile -n com.android.example -f 100` ("keeping the sampling frequency below 200 Hz per cpu"); the current page lists "A device running Android 15+" as the prerequisite (https://github.com/google/perfetto/blob/main/docs/getting-started/cpu-profiling.md).
- simpleperf: `./app_profiler.py -p <pkg> -a .Activity -r "-e task-clock:u -f 1000 --duration 10 -g" -lib <unstripped_dir>` then `./report_html.py [--add_source_code --add_disassembly]`; release apps need `<profileable android:shell="true" />` on Android ≥ Q (https://android.googlesource.com/platform/system/extras/+/master/simpleperf/doc/android_application_profiling.md).
- Macrobenchmark callstack samples: `androidx.benchmark.profiling.mode=StackSampling` (C11) — androidx release notes mention "stack sampling" conversion off the main thread (1.3.0-rc01); the exact backend (simpleperf vs traced_perf) is not stated on the fetched pages (UNVERIFIED).

## D. Audio-specific

### D14. Measuring the audio thread

Android (Oboe/AAudio) — `[usb]` `[farm]`:
- `AudioStream::getXRunCount()` → `ResultWithValue<int32_t>`: "An XRun is an Underrun or an Overrun… An underrun or overrun can cause an audible 'pop' or 'glitch'"; `ErrorUnimplemented` on OpenSL ES; `setBufferSizeInFrames` "By combining this with getXRunCount(), the latency can be tuned at run-time"; `calculateLatencyMillis()` "Calculate the latency of a stream based on getTimestamp()"; `getTimestamp(clockid_t)` → `FrameTimestamp`; "due to issues in Android before R, we recommend NOT calling this method from a data callback" (https://github.com/google/oboe/blob/main/include/oboe/AudioStream.h). `LatencyTuner`: "adjusts the stream's bufferSize by monitoring the number of underruns… Call tune() right before returning from your data callback… Latency tuning is only supported for AAudio" (https://github.com/google/oboe/blob/main/include/oboe/LatencyTuner.h). Callback rule: "You should never perform an operation which could block inside onAudioReady" (https://github.com/google/oboe/blob/main/docs/FullGuide.md). NDK: `AAudioStream_getXRunCount`, `AAudioStream_getTimestamp`, `AAUDIO_PERFORMANCE_MODE_LOW_LATENCY` (https://developer.android.com/ndk/reference/group/audio).
- OboeTester (Play Store `com.mobileer.oboetester`) runs unattended via Intents: `adb shell am start -n com.mobileer.oboetester/.MainActivity --es test {latency,glitch,data_paths,input,output,cpu_load} --es file <name>`; results in `/storage/emulated/0/Android/data/com.mobileer.oboetester/files/`; latency/glitch tests need a loopback adapter (https://github.com/google/oboe/blob/main/apps/OboeTester/docs/AutomatedTesting.md). `dumpsys media.audio_flinger` was not located in a primary doc (UNVERIFIED).

iOS (Core Audio) — `[usb]` `[dev]`:
- `AVAudioSession.ioBufferDuration` ("The current I/O buffer duration, in seconds", iOS 6+) and `setPreferredIOBufferDuration(_:)` (https://developer.apple.com/documentation/avfaudio/avaudiosession/iobufferduration).
- Workgroups (macOS 11 / iOS 14 / tvOS 14 / watchOS 7): "If a client takes too long to produce audio, the thread misses its deadline, which results in an audio overload"; "The system automatically joins the client app's real-time thread to the audio device's workgroup"; extra real-time threads join via `kAudioOutputUnitProperty_OSWorkgroup` (AUv2, "AUHAL or AURemoteIO") or `AUAudioUnit.osWorkgroup` (AUv3), then `os_workgroup_join(workgroup, &joinToken)` / `os_workgroup_leave`; own-deadline threads use `AudioWorkIntervalCreate` (https://developer.apple.com/documentation/audiotoolbox/understanding-audio-workgroups, https://developer.apple.com/documentation/audiotoolbox/adding-parallel-real-time-threads-to-audio-workgroups, https://developer.apple.com/documentation/audiotoolbox/workgroup-management). WWDC20 10224: "If the client takes too long… we get an overload. The user hears this as a discontinuity, or a glitch" (https://developer.apple.com/videos/play/wwdc2020/10224/).
- Instruments: "Audio System Trace" template and "Audio Client / Audio Server / Audio Statistics" instruments exist in Xcode 26.6 (local `xctrace list`), recordable with `xctrace record --template 'Audio System Trace' --device <udid> --attach <proc> --time-limit 30s`; Apple has no public web documentation of their tables (UNVERIFIED schema names for `xctrace export --xpath`). No public iOS API exposes an overload counter equivalent to `getXRunCount` (none found; the owner's engine must count missed deadlines itself, e.g. via `mach_absolute_time` deltas in the render callback).

## E. Unified regression detection / industry precedents

- **Flutter DeviceLab** — `[usb]`-style lab (Flutter's own physical lab): "DeviceLab is a physical lab that tests Flutter on real devices… Tasks specify the type of device they are to run on (`linux_android`, `mac_ios`…)… the test runner reports the success and uploads its performance metrics to Flutter's infrastructure" (https://github.com/flutter/flutter/blob/master/dev/devicelab/README.md). iOS tasks (e.g. `simple_animation_perf_ios.dart`, `new_gallery_ios__transition_perf.dart`, `*_perf_ios__timeline_summary.dart`) set `deviceOperatingSystem = DeviceOperatingSystem.ios` and run `flutter drive --profile [-\-trace-startup] -d <id>`; metrics come from the Dart VM timeline written as `<name>.timeline_summary.json` (`average_frame_build_time_millis`, `90th_percentile_frame_build_time_millis`, `*_vsync_transitions_missed`, iOS-only `average_cpu_usage`/`average_gpu_usage`/`*_memory_usage`); iOS devices are driven with libimobiledevice (`idevicesyslog`, reboot via `idevicediagnostics restart -u <udid>`) (https://github.com/flutter/flutter/blob/master/dev/devicelab/lib/tasks/perf_tests.dart, …/lib/framework/devices.dart). Both platforms' series land in Skia Perf instances `flutter-flutter-perf.luci.app` / `flutter-engine-perf.luci.app` — the same step-fit detector over Android and iOS series (https://github.com/google/skia-buildbot/blob/main/perf/README.md). No xctrace/Instruments in the iOS collection path: it is in-app timeline instrumentation.
- **Chromium**: the chrome.perf waterfall covers "Android, Windows, Mac, and Linux hardware"; no iOS perf bots in the public README (https://chromium.googlesource.com/chromium/src/+/HEAD/tools/perf/README.md). Chromium's iOS test bots parse xcresult only for pass/fail (A2).
- **Firefox iOS**: XCTest perf tests collect "Duration (s), CMT (s): Clock Monotonic Time, CPU Cycles (kC), CPU Time (s), Mem Physical (kB), Mem Physical Peak (kB), CPU Instructions retired (kl), Disk logical writes (kB)" but "don't run as part of the CI test execution for two reasons: There is not a good way to retrieve the data and analyze it [and] To get accurate data it is better to run these tests on real devices"; results were kept in a Google Sheet, not Perfherder (wiki last edited 1 Nov 2021; https://github.com/mozilla-mobile/firefox-ios/wiki/Performance-Tests). Mozilla's Raptor runs on Android/desktop browsers, not iOS (https://firefox-source-docs.mozilla.org/testing/perfdocs/raptor.html).
- **Emerge Tools** (commercial, secondary): "iOS performance testing runs your app on real, physical devices… installed on an iPhone SE 2020… a setup XCUITest is optionally run before the UI test is run repeatedly"; Android on "Google Pixel 3 running Android 12… UI Automator… run dozens of times" (https://docs.emergetools.com/docs/performance-testing, https://docs.emergetools.com/docs/ios-performance-testing).
