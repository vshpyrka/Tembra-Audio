# Технічний звіт: Розробка кросплатформної DAW (Android + iOS) на базі Kotlin Multiplatform та Open Source інструментів

## 1. Архітектурна стратегія: Гібридний підхід KMP та низькорівневих рушіїв

Для побудови професійної DAW обрано гібридну модель, де **Kotlin Multiplatform (KMP)** виступає як клей для бізнес-логіки та UI, а низькорівневий рушій (Rust через FFI/JNI) бере на себе обробку сигналу в реальному часі.

**Обґрунтування та UI-шар:**
*   **Compose Multiplatform:** Використовується для спільного інтерфейсу. Проте архітектор має враховувати, що на iOS Compose базується на Skia, що може призводити до **Metal shader compilation stalls** (затримок через компіляцію шейдерів) при першому рендерингу складних графіків хвиль.
*   **Native Interop:** Для критичних компонентів (наприклад, низькорівневий рендер хвиль) необхідно використовувати `AndroidView` або `UIKitView`.

**Розділення потоків (Control vs Audio Flow):**
Прямий доступ UI до стану рушія **суворо заборонений**. Взаємодія має відбуватися через асинхронні канали:
*   **Control Flow (UI → Engine):** Команди (`Play`, `AddTrack`, `SetParameter`) передаються через lock-free чергу.
*   **Audio Flow (Engine → UI):** Стан відтворення (позиція плейхеда) та дані візуалізації (PCM-піки) передаються назад. При високій частоті оновлення візуалізації JNI-міст стає вузьким місцем. Для Android рекомендовано використовувати **AHardwareBuffer** (shared memory) для zero-copy передачі даних, щоб уникнути витрат на серіалізацію.

## 2. Професійна обробка аудіо та менеджмент часової шкали

**Принципи обробки:**
Аудіорушій оперує спрямованим ациклічним графом вузлів (Directed Acyclic Graph). Кожна ітерація коллбека включає **топологічне сортування** графа для визначення послідовності обробки (Input → FX → Summing).

**Sample-Accurate Scheduling:**
Для запобігання десинхронізації метронома та семплів не можна покладатися на системні таймери UI-шару.
*   **Важливо:** На iOS використання `completionHandler` у `AVAudioEngine` для планування наступного буфера є помилкою — коллбек спрацьовує занадто пізно, що створює чутні розриви.
*   **Рішення:** Необхідно тримати мінімум один **"буфер у резерві"**, запланований завчасно.

**Критичні правила Real-time Hot-path:**
Будь-яке порушення цих правил у аудіо-коллбеку є "смертним вироком" для стабільності звуку:
1.  **Жодного блокування (Lock-free):** Використання стандартних `Mutex` заборонено через ризик **інверсії пріоритетів**. Тільки `try_lock()`.
2.  **Жодної алокації:** Виклик `malloc`, `Vec::push` або `Box::new` може спровокувати Page Fault, що перерве потік обробки. Вся пам'ять має бути пре-алокована.
3.  **Denormal Floats:** При затуханні сигналу процесор витрачає до 100 разів більше циклів на обробку екстремально малих значень. Режим **Flush-to-Zero (FTZ)** та **Denormals-Are-Zero (DAZ)** має бути увімкнений. На архітектурі ARM (iOS/Android) це часто працює за замовчуванням, але на x86_64 (емулятори) потребує маніпуляцій з регістром MXCSR.

**iOS та Unsafe Swift:**
При реалізації `AVAudioSourceNode` на iOS використання стандартних безпечних масивів Swift призводить до зайвих перевірок меж (bounds checks). Необхідно використовувати **Unsafe Swift** (`UnsafeMutableAudioBufferListPointer`) для прямого доступу до пам'яті через покажчики.

## 3. Стек OSS бібліотек та ліцензійна відповідність

Оскільки KMP-обробники працюють у багатопотоковому середовищі, для комунікації між UI та Engine замість SPSC-черг (Ringbuf) слід використовувати MPSC-канали (наприклад, **Crossbeam**), оскільки вони підтримують декілька відправників (Thread-safe producers).

| Бібліотека | Функція | Ліцензія |
| :--- | :--- | :--- |
| **CPAL / AAudio / AVFoundation** | Low-level Audio I/O | MIT / Native |
| **Symphonia** | Декодування (MP3, WAV, FLAC) | MPL 2.0 |
| **Crossbeam / Tokio MPSC** | Lock-free комунікація (MPSC) | MIT / Apache 2.0 |
| **RustySynth** | SoundFont (SF2) синтез | MIT |

**Застереження щодо ліцензій:** Використання бібліотек під ліцензією **GPLv2/v3** (як-от частини коду Ardour) змусить вас відкрити весь сирцевий код пропрієтарного додатка. Для комерційних або закритих OSS-проектів тримайтеся стеку MIT/Apache/MPL.

## 4. Алгоритми тюнера для гітари та віолончелі (DSP)

Для детекції низьких частот (віолончель, C2 ≈ 65.4 Гц) стандартного вікна 1024 семпли недостатньо. Рекомендовано розмір вікна від 4096 семплів при 44.1 кГц та обов'язковий **Zero Padding** для підвищення спектральної роздільної здатності.

**Математичний апарат:**
1.  **Детекція:** YIN або MPM (McLeod Pitch Method) для стабільного пошуку фундаментальної частоти $f$.
2.  **Конвертація частоти в ноту:**
    ```
    n = 12 * log2(f / 440) + 69
    ```
3.  **Розрахунок цільової частоти ноти $f_{target}$ та відхилення (cents):**
    ```
    f_target = 440 * 2^((n - 69) / 12)
    cents = 1200 * log2(f / f_target)
    ```

## 5. Реалізація метронома з нульовим дрейфом (Drift-Free)

Метроном має базуватися на підрахунку семплів, а не системному часі.
*   **Архітектура:** Використовується нативний таймер, що спрацьовує **двічі за період**, щоб гарантувати наявність "буфера в резерві".
*   **Sample-accuracy:** Позиція кліку розраховується як `sample_index = (beat_index * sample_rate * 60) / BPM`.
*   **AssetStore:** Семпли кліків мають бути попередньо завантажені в `HashMap<String, Arc<AudioBuffer>>`, щоб уникнути алокацій при зверненні до них під час відтворення.

## 6. Технічні виклики та стабільність на мобільних ОС

**Android (AAudio/CPAL):**
*   Перерахунок пристроїв (enumeration) у CPAL на деяких пристроях Android викликає **Panic**. Рекомендовано використовувати `default_output_device()` та уникати динамічної зміни конфігурації без потреби.
*   Використовуйте `catch_unwind` у Rust-частині. Паніка в аудіо-коллбеку на Android призводить до `SIGABRT` і миттєвого краху всього процесу.

**iOS (AVFoundation):**
*   **Audio Session:** Мікрофонний вхід (Input Stream) має бути закритим до моменту натискання кнопки "Record". Постійно відкритий вхід призводить до відхилення додатка в App Store.
*   **Unsafe Swift:** Обов’язкове використання `OSStatus` для обробки помилок у нативних коллбеках Apple.

## 7. Висновки та дорожня карта розробки

Для створення стабільної DAW необхідно ізолювати real-time потік від будь-яких непередбачуваних операцій ОС.

**Рекомендації для розробника (Roadmap MVP):**
1.  **Налаштувати базовий I/O:** Використовуйте `AVAudioSourceNode` (iOS) та `AAudio` (Android) з підтримкою **Unsafe Swift** та **JNI Zero-copy**.
2.  **Реалізувати MPSC-канали:** Використовуйте `Crossbeam` для передачі команд від UI до Engine.
3.  **Створити AssetStore:** Реалізуйте пре-алокацію всіх аудіо-ресурсів через `Arc<Vec<f32>>` для запобігання Page Faults.
4.  **Впровадити обробку помилок:** Обгорнути всі виклики рушія в `catch_unwind`, щоб помилка в DSP не "вбивала" UI.
5.  **Оптимізувати графіку:** Використовувати `SharedMemory` для передачі waveform-даних, мінімізуючи навантаження на JNI-міст.
