A · kotlin-concurrency-and-flow

Coroutine ownership and event contracts

The skill asks that every piece of asynchronous work has a visible owner, cancellation path and failure path, and that event primitives are chosen from their replay and fan-out contract rather than by default.

HighA1

The audition job has no owner, so a late decode can revive a cleared audition

shared/ui/src/commonMain/kotlin/audio/tembra/ui/tuner/TunerViewModel.kt:176–188, 314–316 
fun audition(stringIndex: Int) {
    val state = _uiState.value
    val string = state.strings.getOrNull(stringIndex) ?: return
    viewModelScope.launch {
        val sound = sounds.resolve(state.instrument, string.note)
        if (sound is ReferenceSound.Recording && sampleHandles[sound.resourceName] == null) {
            val handle = withContext(decodeDispatcher) { audio.loadSample(sound.bytes) }
            ...
        }
        _uiState.update { it.copy(audition = AuditionState(stringIndex, it.loopTone, sound)) }
        applyAudio()
    }
}
Rule
"Identify each coroutine owner, cancellation boundary, producer, consumer" and "Finish when cancellation, restart, replay, and failure behavior are all observable from the public API and no caller must guess who owns the work." The launch is fire-and-forget: nothing holds its Job, so stopAudition(), screenVisible(false), foreground(false) and a second tap cannot cancel it.
Why

Two orderings go wrong. Tap a string whose recording is still decoding, then tap a second string: the second audition is applied first and the first one overwrites it when its decode finishes, so the card the user tapped last is not the one sounding.

Tap a string, then background the app before the decode completes: foreground(false) calls clearAudition(), the job then completes and writes the audition back, applyAudio() computes Idle because the app is hidden, and the next foreground(true) starts the tone. Spec FR-020 says a tone stopped by backgrounding never restarts. The window is the length of one WAV decode, so it is narrow but real.

Change
Keep private var auditionJob: Job?. In audition() cancel the previous job before launching, store the new one, and check isActive (or use ensureActive()) before the state write. Cancel it in clearAudition() and onCleared(). Add a ViewModel test that taps two strings while the first recording decodes and asserts the second one wins, and one that backgrounds mid-decode and asserts no tone starts on return.
MediumA2

Three collectors are launched from the ViewModel constructor

shared/ui/src/commonMain/kotlin/audio/tembra/ui/tuner/TunerViewModel.kt:72–97 
init {
    viewModelScope.launch { val stored = preferences.snapshot.first() ... applyAudio() }
    viewModelScope.launch { permission.status.collect { status -> ... applyAudio() } }
    viewModelScope.launch { audio.events.collect(::onEvent) }
}
Rule
Structured concurrency, step 4: "Move construction-time and initializer launches to an explicit suspending bootstrap or named launch site. A constructor or Initializer.initialize() may register, but must not launch." The UI exception needs the caller to be "an actual UI event or lifecycle hook"; a constructor is neither.
Why
The practical risk is low here because the ViewModel is entry-scoped, so its lifetime already tracks the Tuner destination. The cost shows in the tests, which must call runCurrent() right after construction before anything is observable, and in ordering: applyAudio() can run from the permission collector before preferences are loaded and relies on the loaded guard to do nothing.
Change
Move the three launches into one named start() guarded by a Job, and call it from the existing lifecycle hook screenVisible(true) (or from TunerScreen's DisposableEffect). The loaded guard can then become an ordering guarantee: load preferences first, then subscribe to permission and events.

androidApp/src/main/kotlin/audio/tembra/android/MicrophonePermissionHost.kt:45–51

Rule

shared/engine/src/androidMain/kotlin/audio/tembra/engine/AndroidAudioFocus.kt:17 · shared/engine/src/iosMain/kotlin/audio/tembra/engine/IosAudioSession.kt:45 · shared/engine/src/commonMain/kotlin/audio/tembra/engine/TunerAudio.kt:35–36

E · compose-performance

What recomposes at 10 Hz

The skill wants a provable path before a repair and a measurement after. Only source was available here, so E1 names the path and gives the repair conditionally; the meter's own draw loop is already built the way the skill asks.

MediumE1

Every 10 Hz reading recomposes the whole tuner tree, and the selector bar rebuilds its lists each time

shared/ui/src/commonMain/kotlin/audio/tembra/ui/tuner/TunerViewModel.kt:283 · TunerScreenContent.kt:35 · TunerSelectors.kt:33–35 
// TunerViewModel.poll(), 10 Hz while listening
_uiState.update { it.copy(audio = engineState, reading = reading) }

// TunerSelectors, runs on every recomposition
val instrumentItems = Instrument.entries.map { SegmentSpec(it.id, it.label, ...) }
val stringItems = GuitarStringCount.entries.map { SegmentSpec(it.count.toString(), it.label) }
val modeItems = TunerMode.entries.map { SegmentSpec(it.id, it.label, ...) }
Path
While a pitch is heard, poll() writes a new TunerUiState ten times a second. TunerUiState holds a List<TuningPreset>, so the compiler treats it as unstable and compares it by identity; every emission is a new instance, so TunerScreenContent, TunerSelectors and AutoListenPane all recompose. TunerSelectors then allocates three new lists and passes them to three TembraSegmentedControls, whose List<SegmentSpec> parameter is likewise identity-compared, so each segment recomposes too. None of this touches the meter's frame loop, which is correct.
Rule
Stability: "Lazy item gets a new lambda or derived object each parent recomposition → Hoist/remember it for the item's stable inputs" and "UI state exposes List … that must be immutable → convert once at the boundary." Diagnosis: "When only source code is available, separate the proven feedback path from its unmeasured runtime cost."
Change

Two cheap steps, then measure. First, hoist the three constant lists to file-level private vals; they depend only on enum entries. Second, give TunerSelectors and ByEarPane the fields they read (instrument, string count, mode, pill; preset, presets, loopTone, audition) instead of the whole state, so a reading-only change lets them skip. If you would rather keep the single-state signature, annotate TunerUiState with @Immutable (truthful: every property is a val and the list is never mutated) and accept that reading changes still recompose the bar.

The runtime cost is unmeasured. Ten recompositions a second of about twenty nodes is unlikely to show as jank on its own; the value is keeping the pattern clean before the timeline and mixer screens, which will carry far more nodes under far faster telemetry.

H · compose-ui-testing-patterns

The Compose UI tests

All 26 test files under uiTest, androidDeviceTest and androidTest were read in a second pass. The suite already does most of what the skill asks: every tuner test drives TunerScreenContent with a plain state and no-op callbacks, clocks are frozen wherever the meter's frame loop or a fade is composed, and semantics are asserted before any pixel is probed. The findings share one root cause: the design-system item composables create their own MutableInteractionSource, so hover and focus visuals can only be reached through platform input.

MediumH1

Hover on the bar, the rail and the segmented control is proven by simulated mouse input

uiTest/…/designsystem/TembraNavigationBarTest.kt:158 · TembraNavigationRailTest.kt:143 · TembraSegmentedControlTest.kt:111

// production side, the seam that is missing:
private fun NavigationBarItem(...) { val interactionSource = remember { MutableInteractionSource() } ... }   // TembraNavigationBar.kt:90, 99
private fun NavigationRailItem(...) { val interactionSource = remember { MutableInteractionSource() } ... }  // TembraNavigationRail.kt:91, 101

Do not simulate pointer or mouse events: that is environment-dependent and flaky." and "Always inject MutableInteractionSource, never rely on its internal default."
Why
The hovered colour comes from collectIsHoveredAsState() on a source the test cannot reach, so the tests go through each platform's pointer pipeline. They are green on both lanes today; whether a synthetic move produces a HoverInteraction.Enter on the next Compose Multiplatform release is the dependency the skill names. The rail test also probes a single pixel for the hover fill, so it is doubly sensitive. The skill allows broadening production here because "that production boundary is itself under test".
Change

In the test, create the source, pass it for the item, TestScope().launch { source.emit(HoverInteraction.Enter()) }, waitForIdle(), and keep the existing colour assertions.

What already matches the skills

Nine places the code does what a skill asks for

Restraint is part of every skill in this set: each one says to finish with no change when the existing owner or seam is already right. These are the places where that is the verdict.

  • Screen seams. TunerScreen wires the ViewModel and lifecycle; TunerScreenContent takes TunerUiState plus TunerCallbacks and is what the UI tests drive. NavigationShell / NavigationShellContent follow the same split. This is exactly the three-seam boundary in compose-state-and-effects.
  • Frame-rate reads stay in draw. rememberFrameTick writes a LongState from withInfiniteAnimationFrameNanos and only the Canvas lambda reads it (TunerMeter.kt:113); the needle smoother and the pitch snapshot are plain remembered objects mutated in draw. That is the deferred-reads pattern applied to a 60–120 Hz signal.
  • Animated state read in draw or graphicsLayer. TembraSegmentedControl's fill, TembraToggle's track and knob, TembraStatusPill's alpha and StringCard's level bars all read their State inside drawBehind or graphicsLayer {}.
  • Read-only theme accessors. Every TembraTheme getter reads a CompositionLocal or MaterialTheme value and nothing else, which is the precise contract @ReadOnlyComposable requires.
  • Lifecycle-aware collection. Both screens use collectAsStateWithLifecycle, and LifecycleStartEffect / LifecycleResumeEffect pair every registration with its dispose.
  • Platform boundaries are semantic. MicrophonePermission, AppDirectories, TunerAudio and ResourceReader expose no Context, Activity, AVAudioSession or resource ids in commonMain; the Android permission host binds to the Activity explicitly with attach / detach instead of hiding it behind a Context.
  • Value class where it earns it. SampleHandle is a @JvmInline value class; the multi-field types (Note, MeterReading, TuningPreset) are data classes. ReferenceSound.Recording overrides equality for its ByteArray, which a value class could not do.
  • Exhaustive when over sealed results. DesiredAudio, AudioEvent, ReferenceSound, Destination and AudioStatePill are all matched case by case with no else, so adding a case fails to compile at every site that must handle it.
  • Cancellation is preserved. The only catch in production code catches MissingResourceException, not Exception, so CancellationException always propagates. The 10 Hz poll checks isActive and is cancelled by both updatePolling() and onCleared().
